Three approaches for canary.growdirect.io/rapidpos

Technical audience first — architecture, how RapidPOS works, what you build on it. Pitch deck ("Store of the Future 2030") embedded as a section within.

A

Single-file HTML — Designed Document

One self-contained index.html, like the current Armstrong proposal. Sections scroll top-to-bottom: Overview → Architecture → MCP Endpoints → Integration → Store of the Future 2030. Wiki pages from NCR vault are manually embedded as styled sections. Deploy via gh api PUT — no build step.

Pros

  • Ship the same day
  • Full design freedom — Claude.ai generates it
  • One file, zero tooling

Cons

  • Gets unwieldy past ~2,000 lines
  • Wiki content updates = manual copy-paste
  • No URL-addressable pages for individual topics
B

Multi-page Static HTML — GitHub Pages repo

New growdirect-llc/canary repo. Each section is a separate HTML file (index.html, architecture.html, endpoints.html, store-2030.html). Shared CSS + nav component. Wiki pages become their own HTML files, same styles. GitHub Pages serves root at canary.growdirect.io, subpath /rapidpos/ served from a subfolder.

Pros

  • Each page URL-addressable — linkable to specific content
  • Easier to maintain — edit one page at a time
  • Wiki pages feel native, not bolted on

Cons

  • More files to keep in sync visually
  • Shared nav/CSS still manual (no build step)
  • Wiki updates still manual
C

Quartz v4 Vault — Matches existing infrastructure

New growdirect-llc/canary repo as a Quartz vault, just like NCR / CRB / CATz. Markdown files for every section. GitHub Actions builds and deploys. canary.growdirect.io resolves to it. Wiki content flows directly from Brain exports — same pipeline as other vaults. Add a custom landing page for the RapidPOS pitch section.

Pros

  • Fits the existing vault pattern — zero new infra
  • Wiki pages are first-class — backlinks, graph, search
  • Markdown = easy content updates from Brain

Cons

  • Quartz design is opinionated — pitch deck sections need custom CSS work
  • Store of the Future visual treatment harder to achieve
  • Build step adds deploy latency (~2 min per push)

My recommendation

B — Multi-page static HTML. Gives you URL-addressable sections (linker a CTO to the endpoints page directly), full design control for the Store of the Future section, and a clean separation between proposal pages and wiki pages — all under one consistent stylesheet. Claude.ai generates the initial design; deploy as GitHub Pages. Scale to Quartz later if content volume demands it.
