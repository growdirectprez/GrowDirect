Globalization at SAP

In general terms, globalization is the process of designing and developing products and services for a worldwide market.  It addresses all of the enterprise issues associated with making a company truly global.  For the globalization of products and services this involves integrating all of the internal and external business functions within logistics, marketing, sales and customer support in the world market.  It consists of two aspects – internationalization and localization.  

Internationalization is the process of generalizing a product so that it can handle multiple languages and cultural conventions without the need for redesign.  Internationalization takes place at the level of program design and document development.  For SAP, this ensures that the SAP solution set is suitable for use in multiple cultural and technical environments, and that they support localization processes.

Localization is the process of adapting software to the needs of a particular country (or "locale") and it consists of two major aspects – functional localization and linguistic translation.

These definitions are derived from the standards of  HYPERLINK "http://www.lisa.com" www.lisa.com (Localization Industry Standard Association).


Language Version (Linguistic Translation) versus a Country Version (Functional Localization)

Language versions and country versions are not the same.  

Language versions refer to the level of translation for SAP software shipments. 
Country versions refer to the adaptation of SAP's software (coding and customizing) to cover legal requirements and common, local business practices.  The logic of the software solution works independently of the language version used.  

SAP solutions follow global best business practices, with specific functions and features to account for varying national tax laws, accounting laws, and manufacturing regulations in over 40 countries.  Katz can run all country versions simultaneously in the same system and each user can logon in their preferred language, with almost 30 languages to choose from.

Low (Priority 4) - A message should be categorized with the priority "Low" if the problem reported has few or no effects on normal business transactions.  The problem is caused by an incorrect or inoperable function of the SAP system that is not required daily or only used very rarely.

4.1.17 Disaster Recovery

Please provide any details you may have regarding available disaster recovery services.  These may be provided by yourself or a certified partner.

SAP supports disaster recovery services through close partnerships with certified hardware and software partners.  A disaster is a situation in which critical components in the SAP environment become unavailable so that service cannot be resumed in a short period (less than a day as a general rule).  A typical situation would be destruction of the hardware due to fire.
Protecting SAP application host running enqueue and message services can be achieved by having a standby system available (at a remote site) that can be started up in the event of a disaster. If a standby system, which could also be another application server that has been reconfigured, is started to provide the critical SAP services, all other application servers have to be restarted.

To protect the database, the entire database can be replicated with a method provided by the various database vendors.  This approach is known as "Hot Site Backup" or "Standby Database."  This means that the functionality to achieve replication is built into the database service instead of having to be coded by the client applications.  These products follow the concept of "replication transparency":  Oracle Standby Database, Informix HADR, Replicated Standby Database for IBM DB2 UDB on Windows/Unix/iSeries/zSeries and Microsoft SQL Server Standby Database.  SAP supports these standby database solutions from SAP certified partners but may require additional licensing.  SAP also works with hardware partners like EMC to support disaster recovery solutions like EMC SRDF and TimeFinder.

All updates already made are reversed. 
The user receives an express mail indicating that the update was unsuccessful.
The locks are released and a system entry is made in the system log.

4.4.3 Application Version Management Tools

Please describe any application version management tools that are available for your system.  Your response should indicate if there are any additional costs for the tool and the developer of the tool.  If there are no version management tools please describe the recommended version management approach.

SAP software comes with a full development environment that includes an application version management utility called the Transport Management System (TMS).  All version control of SAP objects is managed with the development environment.  When a change is to be made, an object related to the change is assigned to a change request.  This change request uniquely identifies one or more objects that are the subject of some change in the system.  The Transport Management System manages the orderly migration of change requests from development through production.  An authorized individual must approve all change requests before being released to production.

The infrastructure that SAP recommends to support effective change management is a three-system landscape with separate development, test and production systems.  

It is within the development system that any changes necessary to configure the application are performed.  Objects that are the subject of change are allocated to a change requests.  Any object that is allocated is checked out thus eliminating parallel change to an individual object.  When all changes are complete in development, the change request is released for transport to the test system.  

Within the test system, full system testing is performed.  If the changes test successfully, they are transported to production.  If the changes do not test successfully, appropriate changes are made in development and the change is re-migrated to the test system.  Changes are only introduced to production once they have been successfully tested in the test system.  Any changes that are introduced into production are first tested in a test partition before being introduced to an active production partition.

If changes have to be backed out of production, this is done with a correcting change request that effectively overwrites the unwanted change with the prior version.

In order to deploy an effective test environment, most SAP customers deploy a fully copy of production data.  At suitable intervals test data can be refreshed by restoring a production backup.  Alternatively, one can also perform a test refresh with a production mirror split that is subsequently merged with the test disks.
