Business and Creative Design Stage Overview


Creative Treatments & Concepts

Overview
The creative treatment process involves a high level of creativity from the design team.  With input from the users, the objective now is to stretch the creative limits of that box without breaking it.  With the design parameters already in place the designers can begin putting together the treatments and concepts that will ultimately led to the final "look and feel" of the site. The client can expect to see a variety of ideas here.  

 
Approach
The process involves the development of full color rendering suggesting final “look and feel”.  This process is normally performed in one of two ways:
The design team generates a variety of creative concepts that best represents the client needs based on the designated design parameters.
The design team not only expands on the creative ideas that are found on the existing site, but also infuses new ideas to ensure the freshness of the "look and feel".

No matter the approach, multiple treatments are submitted for client review.  
  
Work Product
A creative treatment is typically a Photoshop mock-up of the web page layout, to define colors, images or a 'user experience'.

Web Page and Graphics Layout Finalization

Overview
Working through the best of the ideas that have been presented, the user team
selects master treatments in order to establish the overall "look and feel."  At this point the creative team can begin the design and apply this treatment to both the static and dynamic HTML templates.
 
Approach
The web page and graphics layout finalization is an iterative refinement process.  The design team works closely with the user team to mix and match elements and build consensus toward one design.  The ultimate goal of the exercise is to gain client approval of the master treatment and generate templates in order to establish the cornerstone for all subsequent HTML generation.
  
Work Product
The work product is typically a Photoshop mock-up of multiple HTML templates for both the static and dynamic templates.

HTML Development

Overview
This step of the design is comprised of the HTML development for both the static and dynamic pages. This is the first step that begins to bridge the gap between the "look and feel" of the site and the functionality of the site. The development of the HTML is heavily dependent upon the preceding steps as input into the process.  The functional storyboards, "elected" creative treatment and the finalized web page/graphics layout are the key inputs into this process.
 
Approach
The output from the web page finalization will serve as the primary input into the HTML generation (e.g., PhotoShop files).  Portions of graphics and elements will be extracted from the Photoshop files and entered in the HTML generation tool.  Once completed the dynamic HTML templates will be handed off to the BroadVision JavaScript developers to continue with the design and construction of the dynamic content.  The static HTML will be considered complete at the end of this step.
  
Work Product
The output to this process is the HTML file typically created using an HTML generation tool (e.g. Dreamweaver, etc).

Categorization Hierarchy & Content Types

Overview
The content types and categorizations identify how content will be organized at the highest level.  This analysis is performed after the user content needs analysis.  The analysis is the logical grouping of the existing content needs and this categorization eventually will serve as the content hierarchy.  
 

Approach
The approach to obtaining the content categorization is to work through the user content needs list and to “bucketize” or group related needs into logical categories and sub-categories.  Doing this should also take into account how rules will be targeted and implemented against content.

The approach to obtaining the content types as a rule should generally utilize the BroadVision out-of-the-box content types (editorials, products, advertisements, etc.) unless special access rights are needed to utilize the One-To-One Command Center.

  
Work Product
The typical working document is a matrix form managed in a MS Excel worksheet that provides ease of manageability and organization.  The needs list is also cross-referenced to the categories by adding an additional column to the needs list which holds the related category/subcategory.  The user content needs list will be organized by content type, categories and subcategories.    
 
Input
Preliminary categorization based on content needs, wireframes, preliminary site map/flow, preliminary business rule list, user segementation and client personnel who are familiar with existing content and site personalization strategy.

Content Migration Process

Overview
The content migration requirements identify the steps needed to migrate content from the current content environment into the BroadVision system.  This analysis is performed after the content inventory and user content needs exercise.  The information can be identified either in a separate content migration requirements document or simply as additional column headers on the content inventory matrix.  Migration requirements may be identified on an item-by-item basis or on small groups of related items at a topic basis.  
  

Approach
The approach to obtaining content migration requirements is primarily achieved through working through the content inventory and identifying the different types of content that need to be integrated into the BroadVision system.  Different types of content may require varying levels of migration effort.  This can include external content feeds, existing static content, existing dynamic content, etc.  The migration process should identify what level of migration effort will be targeted for these different content items/groups.
  
Work Product
The typical working document is prepared and managed in an MS Excel worksheet in a matrix form that provides for ease of manageability and organization.  Typically, the content migration requirements document contains headers such as complexity, migration method and potential migration issues.
 
Input
Completed content inventory and client personnel who are familiar with existing content and architecture.

Content Attributes (Metadata)

Overview
Content attributes provide information about content that help determine its relevancy to a user.  This information, or meta-data, are descriptors of content and can include data information (creation date, start date, end date, title, text, etc.) and matching information (industry, segment, etc.).  This information is used to identify content records so that they may be dynamically served to a user based on the matching of a business rule against the content attribute(s).
 

Approach
The approach to obtaining content attributes is to identify how content will be used on the site to satisfy particular user’s needs.  Doing this should also take into account the different ways content will be served throughout the site.  This also may take into account the different business rules that will be implemented to ensure that the appropriate attributes are identified to satisfy these rules.

  
Work Product
The typical working documents are matrices based on content type such as editorial, products and advertisements that break out attributes for each content category and subcategory as identified in the content categorization.  This document is prepared and managed in an MS Excel worksheet in a matrix form that provides for ease of manageability and organization.  Typical column headers include content category, subcategories, attributes and related attributes.
 
Input
Completed content categorization, user segments, wireframes, preliminary site map/flow, preliminary business rule list and client personnel who are familiar with existing content and site personalization strategy.

Content Authors, Roles and Workflow

Overview
Authors, roles and workflow provide the information necessary to determine the individuals responsible for creating, tagging and approving content within the BroadVision system.  This exercise also determines the responsibilities of each individual involved as well as the overall process used to track and edit content from creation to publishing.  
 

Approach
The approach to identifying authors, roles and workflow is to identify the different processes needed for creating, tagging and approving content within the organization   as well as the individuals involved and their roles within the process.  Once a set of standard workflows are identified, each category is mapped to a specific workflow that will be used to publish that type content.  Often, one workflow will apply to many different categories.  For example, certain content categories may require legal approval prior to publishing.  In this case, a separate workflow will be needed to account for this step in the approval process.  These workflows are often based upon existing workflows within the organization that are translated into the publishing environment.  

  
Work Product
The typical working document is a set of matrices and diagrams that identify the authors, roles and workflow associated for different content categories requiring separate workflow processes.  This document is prepared and managed in an MS Excel worksheet in a matrix form that provides for ease of manageability and organization.  The typical column headers that identify this information include workflow name, state name, access group, description, start state, next state and attribute assigned.

 
Input
Completed content categorization and client personnel who are familiar with existing content and workflow processes.

 Content Management Templates

Overview
Content templates provide the information necessary to create, tag and submit content with the appropriate attributes into the BroadVision system.  These templates provide an easy mechanism for various and distributed content creators and editors to create, tag and submit content.  
 

Approach
The approach to identifying content templates is to examine the types (and categories) of content that will be published on a frequent basis into the BroadVision system.  To ensure the appropriate information is published into the system, the templates must include the attributes for the content category.  These attributes become the fields that content creators and editors use to create, tag and submit content.  These fields can be text fields, radio buttons, drop-down boxes, etc. to facilitate efficient and consistent content publishing. 

  
Work Product
The typical working document is a matrix based on content categories that break out attributes and corresponding attribute values.  This document is prepared and managed in an MS Excel worksheet in a matrix form that provides for ease of manageability and organization.  Typical column headers include content category, subcategories, attributes, related attributes, and corresponding attribute values.
 
Input
Completed content attributes and client personnel who are familiar with existing content and site personalization strategy.

Organizational Readiness New Structure

Overview
A new web technology will normally have an impact on the structure of the organization.  As process changes are defined for maintaining dynamic personalized content, new roles and responsibilities are identified, information on the impact to the organization structure must be gathered.  A new structure is designed to account for process changes and new roles and responsibilities. 


Approach
The approach to designing organization structure is to identify the necessary activities. Then create a logical grouping of theses activities in an appropriate hierarchy. Next, prepare a description of all the various relationships. 

  
Work Product
The typical working document will be an organization chart indicating the relationships between divisions, units, groups, and/or individuals. This document is prepared and managed in either of the following: MS Excel worksheet, MS PowerPoint, or Visio. Also, textual information describing the relationships between various units can either appear on this chart or when extensive detail is available in an MS Excel or MS Word document. In the case of extensive detail, typical column headers that identify the information include entity x, entity y, relationship type, and relationship description. 

 
Input
Organization charts and information provided by personnel familiar with the organizational structure. Personnel familiar with the new process flows, structure hierarchy, and job roles.

Organizational Readiness Job Profiles

Overview
Based on the analysis completed concerning the current skills inventory by job 
and the envisioned job design created, determine the skills gap between the 
current jobs and target job design. Job profiles will be created for existing jobs with changes in responsibilities and new jobs created.


Approach
The approach to determining the skill gap is to enumerate the skills necessary for the new organizational structure. This skill set for the target environment should be compared to the current skill set. This comparison will identify the skill gap from the current structure to the target structure. Also by job, identify the skill requirement gaps. This level of skill analysis will be dependent upon the HR practices of tracking skill requirements by job. Finally, after collection of this information create job descriptions for all new positions and document any changes to existing jobs.

  
Work Product
The typical working documents will be a job description chart that can be prepared and managed in MS Word or MS Excel. Typical column headers that identify the information are job title, tasks, output, tools required, skills required, performance measures, etc.

 
Input
Sources of information can include the following: skills inventory of current structure, organization chart for target environment, business unit leaders, senior management, personnel department, recruiting manager, work plans, and previous or concurrent activities such as Organizational and process mapping.

Consistent process documentation techniques should be used throughout the documentation, assessment, and design/redesign of business processes. One form of process documentation is called a process map. Using standard process mapping symbols, process maps can be used to graphically represent the decomposition of a business process into an interdependent chain of process units at one or more discrete levels of abstraction, and to identify the business process's inputs/suppliers and outputs/recipients.

To help team members remember the elements of a process map, the mnemonic SIPCO may be used: Supplier, Input, Process, Customer, Output.

Sample Work Product  - Process Flow Diagram

Process maps can be drawn at various levels of abstraction, ranging from maps that indicate what work is done (i.e., decomposition to the elementary process level) to how work is done (decomposition of the elementary processes into constituent tasks and steps): 
Level 1 maps: Each process area symbol represents either a value-chain or support process area. 

Level 2 maps: Each Level 2 map represents a decomposition of one of the process areas depicted on a Level 1 map. The Level 2 map below is a decomposition of the Order Management process area on the Level 1 map (i.e., 1.0 Order Mgmt.). 

Level 3 maps: Each Level 3 map represents a decomposition of one of the Level 2 process areas. Each box on the level 3 map represents either a lower-level process area or an elementary process (if the Level 2 process area is a primitive process area). 
Beyond Level 3. Each additional level represents a further decomposition of the process units depicted on the preceding level (e.g., if the Level 3 map depicted elementary processes then the Level 4 map would depict tasks, and the Level 5 map would depict steps). 
Note: At each level, boxes are connected by arrows to indicate the direction of output flow and to represent that box's output. The arrows must be labelled with the output (or outcome) of the preceding box.
Sample Work Product - Process Cross-Reference

Process mapping should always begin at the top (Level 1), whether the scope of the project includes the entire enterprise or just one process, function, or business unit. 

Since most changes take place at the task level when processes are redesigned, it is generally not necessary or appropriate to develop process maps at lower levels of decomposition.
Tasks may be cross-referenced to the business units having responsiblity for them in the current environment. Such a cross-reference facilitates the linkage of organizational costs to tasks and can reveal issues that need to be resolved to enable performance improvement. One way to represent this cross-reference is to indicate functional boundaries in the Business Process Map at the level depicting constituent tasks.

JavaScript Best Practices

Performance Considerations
The following JavaScript coding tips are general coding tips. 
Avoid crossing the JS/C++ boundary wherever possible:
var list = category.childContent();
for (i = 0 ; i < list.length; i++) 
{
   Response.write('<TD>');
   Response.write(list.get(i).SKU);
   Response.write('</TD><TD>');
   Response.write(list.get(i).PRICE);
   Response.write('</TD>');
}

This could be better done:
var list = category.childContent();
var length = list.length;
for (i = 0; i < length; i++) {
   item = list.get(i);
   Response.write('<TD>' + item.SKU + '</TD><TD>' + item.PRICE + '</TD>');
}

Don't use localRedirects(visitScript)
if (btn == 'OK') 
{
   visitScript('ok.jsp');
} 
else 
{
   visitScript('cancel.jsp');
}

localRedirect is a very slow operation and should only be used in error pathways.  If you must jump to another script, use server-side includes:
function ok_script() 
{
   %> <!--#include file = "ok.jsp" --!> <%
}

function cancel_script() 
{
   %> <!--#include file = "cancel.jsp" --!> <%
}

if (btn == 'OK') 
{
   ok_script();
   RETURN();
} 
else 
{
   cancel_script();
   RETURN();
}

Avoid contentByQuery and contentByCondition.  
It always makes a query directly to the database, which can be a major drain on system performance.  Many times, you can structure your application flow to use methods that get data from the cache, which is several orders of magnitude faster.
Take advantage of the Process and Session objects.  
If there is data that you have to compute or retrieve from the database, get it once and stuff it in the Process object.  Use accessor functions for this type of data:
function getStateList() 
{
   var stateList = Process._STATE_LIST;
   if (stateList == null) 
   {
      stateList = cntMgr.contentByQuery("SELECT * FROM STATES",0);
      Process._STATE_LIST = stateList;
   }
   return stateList;
 }

If you want to put a navigation bar on every page, compute the HTML for it once for the session, put the string in the Session object and then for each page, retrieve it and blast it out to the browser directly.
Take advantage of native JavaScript objects when returning data from functions.  
JavaScript does not have "out" parameters, but you can construct native objects and stuff as many properties as you like:
function getTotals() 
{
   var ret = new Object();
   ret.subtotal = computeSubtotal();
   ret.taxes = computeTaxes();
   ret.total = ret.subtotal + ret.taxes;
}

Use native JS objects(or BVI_Properties if you need persistance) as hash tables.
var noises = new Object();
noises['dog'] = 'bark';
noises['cat'] = 'meow';
noises['pig'] = 'oink';

for (x in noises) 
{
   print('noises.' + x + ' = ' + noises[x]);
}

Property lookups like this in JavaScript are pretty quick.  Don't do linear scans through arrays if you can avoid it.
Be careful with function naming.   
Functions are cached by the system, and the names are global across all scripts.  If you have two functions with the same name in two different scripts, you can see some very strange behavior.  Add the following line to your startup scripts:
warnIfFunctionRedefine(true);

This will generate messages in the error log to let you if this happening.
Avoid <%= syntax, or use the optimizer.  
Each usage of the <%=(or shortcut), will cause a call to Reponse.write which is an extra cross.  This comes up a lot when making tables:
<TD><%= name %></TD><TD><%= sku %></TD><TD><%= price %></TD>

This will be translated to:
Response.write('<TD>');
Response.write(name);
Response.write('</TD><TD>');
Response.write(sku);
…

It's much better to concatenate stuff together and send it out with one Response.write:
Response.write('<TD' + name ...);

Use the script optimizer and fastconcat.  
"fastconcat" is a JS primitive function that does string concats about 2-3x faster than using groups of '+'.  The script optimizer cleans up whitespace and removes comments.  It also removes the <%= and makes them into fewer crosses.  Tests have shown about a 25% speedup on average(your mileage may vary).
Use the cursor in the BVI_ContentList:
var list = getList();
var length = list.length;
for ( i = 0; i < length; i++) 
{
   var row = list.get(i);
   print(row.SKU);
}

The cursor lets you avoid creating an extra variable:
var list = getList();
var length = list.length;
for ( i = 0; i < length; i++) 
{
   list.cursor = i;
   print(list.SKU);
}

JavaScript Architecture
Critical to the success of any BroadVision implementation is a JavaScript Architecture.  The intent is to solve recurring architectural issues, provide common components, and provide a consistent approach to JavaScript development.  Thereby reducing the burden on individual developers, providing a framework for reuse, and increasing the maintainability of the code.
This architecture lays such a foundation.  It provides a general structure for integrating JavaScript into static HTML templates.  It also provides common components, including an API for dealing with CGI environment variables.
Script Types
The framework is composed of several layers:

Layout Script
Draw Script
Manager Script
BV Script

Layout Script
Most pages on a site follow a common pattern.  For instance, pages often have a main area, with a toolbar to the left, and a console along the top of the page.  The layout script encapsulates the generation of this HTML.

The layout script is responsible for generating the HTML that defines the overall layout of a page, without generating HTML for a specific area of the page.  Embedded within the layout script should be appropriate callScript’s to generate each specific area.

Following the above example, the layout script would define the HTML to place the toolbar, console, and main areas in relation to each other or the page as a whole; however, the script would not generate the HTML for the specific areas of the page.

When naming layout scripts, the name should end in ‘Layout.’  For example : StandardLayout, PopupLayout.

Draw Script
The draw scripts are responsible for generating the HTML for a specific area of the page.  Additionally, a draw script should handle any actions (form posts or url links that require processing)*

If a draw script is complex or easily factorable, an effort should be made to us callScripts to factor this page into separate areas.

In order to maximize the separation of JSP and HTML an effort should be made to do all of the JSP processing at the top of the script.  Additionally, use of manager scripts should be used to do any non-trivial processing.

Examples of draw scripts are : Toolbar.jsp, Console.jsp, Login.jsp, HomePage.jsp.

Manager Scripts
In order to increase the separation of JSP and HTML use manager scripts to do any non-trivial script processing.  One of the advantages here is this script is a candidate for conversion to a component.
The manager script should define a class with appropriate methods.  To make this class available a global variable should be defined with the same name as the class, except using a lower-case first letter.

When naming manager scripts, the name should end in ‘Manager.’  For example : StandardLayout, PopupLayout.

A Concrete Example:
 EMBED Visio.Drawing.6  
Fleet.jsp
Responsible for reading in the CGI environment variable ‘pgClass’ and determining which scripts are needed to realize the page.
PageDef.jsp
Maps individual pgClass’s to a layout script and any additional scripts necessary to fill in framework layed out by the layout.
Layout.jsp
This script generates the HTML to draw the framework of a page.  Multiple layout scripts are generally necessary for one site.  Examples could be : Layout  (Used to draw a page with a toolbar and console) PopupLayout (Used to draw a simplified page for use with popup windows).
Toolbar.jsp
This script generates the HTML to draw the toolbar.  It is called from a layout script
Console.jsp
This script generates the HTML to draw the top console.  It is called from a layout script
Login.jsp
This script generates the HTML to draw the main portion of the login page.  It is called from a layout script.  The first half of the script is used to process any actions (form submits) that may occur on the page.  The action handler will typically make calls to a manager object to do the bulk of the processing.  The second half of the script should make calls to a manager object to retrieve content and display this in the HTML.  The JSP calls should be separated from the HTML as much as possible.
LoginManager.jsp
Wraps the BV API’s.  The bulk of the JSP processing should occur here.

Handling Actions
Draw scripts should handle any action within that page.  The cgi environment variable ‘action’ should be set to indicate the page should process an action.
<%
if (Request.value (‘action’) == ‘login’)
{
	...
}
%>
...
<input type=”submit” name=”action” value=”login”>
...

Caching
Instead of recomputing expensive operations each time a page is viewed.  An alternative is to cache the results of the operation the first time, and then reuse the results for a period of time.
When deciding whether to cache specific information, the developer should consider the how expensive the operation is, how often the data will be accessed, how much memory it will take to cache the data, and if BroadVision already caches the data.
Caching should occur within a manager script if possible.  The data should be stored either on the Session or on the Process, depending if the data is specific to the current user.  The name of the property on the Session or Process should always start with the name of the specific manager class or draw script and an underscore. Session.HomePage_data.
Additionally, when using cache, it is important to set a timeout for the cache.  Use the FLEET_CONFIG table to set a timeout for the specific cache.  The name should start with CACHE_TIMEOUT_ and end with the name of the cache (in upper case).  Following the above example : CACHE_TIMEOUT_HOMEPAGE_DATA.

Overview

The performance analysis should be conducted at a high level, focusing on a few critical transactions. 

With an understanding of the implementation environment, the capabilities and deficiencies inherent in the selected DBMS(s), and the expected access volumes against each entity, the data model may be modified to improve potentially problematic accesses.

For each performance-sensitive transaction identified, response times are analyzed and estimated.  If the results are expected to be outside acceptable limits, alternative data structures are considered for improving the access efficiencies.

Develop Data Dictionary – (Optional)

Overview
A data dictionary, describes what is in the database and contains textual definitions of data elements and objects, as well as physical representation information (e.g., size, precision, ranges, default values, dependencies on other data elements, relationships with other data elements, and frequencies). A data dictionary can store definitions of conceptual or logical objects without regard for implementation as well as physical objects that have implementation characteristics. Definitions of non-automated data may also reside in the data dictionary. 

A data dictionary can provide many benefits to an enterprise, including: 
Maintenance and enforcement of standard data definitions and names by the DA. The data dictionary is the repository for standard definitions and is used to disseminate definitions to programmers, analysts, and database designers. The data dictionary also serves as a mechanism for receiving and approving definitions used by various projects. 
Visibility and resolution of data redundancies in different implementation objects. The average large organization has many redundant and inconsistent definitions, names, and measuring units (e.g., pounds vs. feet) for data objects that can best be compared and resolved using the data dictionary. 
Cross-referencing and reporting on where data objects are used. Where-used reports can be used for impact analysis of a proposed change to an application or data format (e.g., all modules using a particular data element can be identified). These reports can also be used to review proposed system revisions. 
Systems analysis. The data dictionary stores resource information about processes (e.g., transaction volumes) and data in support of system analysis tasks. 
Systems administration. The data dictionary stores information about the data processing environment including programs, job streams, and users that can be used to aid in overall systems administration. 
Project management assistance in controlling the development and maintenance of applications 
Database administration to assist in the design and maintenance of database structures 
Communications administration. The data dictionary stores information about data processing equipment such as location and type of terminals, communications links, and CPUs. 
Document control. The data dictionary can complete document tracking and control functions for specifications, user manuals, test reports, or models. 
Change and configuration control. The data dictionary can track changes to applications throughout the life cycle. 
Programming support through the provision of copy libraries, test data, and data language definitions. 
Provide on-line help to applications users. The data dictionary can be accessed live (with appropriate levels of security) by users to display data definitions. 




Approach
Define each attribute in the data model to its final level. This definition should include location, size, format, edit, and value information. 
Other issues to address include: 
Relative positioning within an entity where relevant (particularly for links based on foreign keys or internal sort keys) 
Syntax and edit values for range limits and all non-dependent and dependent edit rules 
Data type (e.g., numeric, alphabetic) 
Internal storage format (e.g., binary) 
Unique formats (e.g., date as yy/mm/dd or mm/dd/yy or dd/mm/yy) 
Default display formats (e.g., the '/' in dates, thousands comma separators, number of display decimals) 
Number of storage positions occupied 
Number of decimal or binary positions for numeric elements 
Whether zero suppression is to be used 
Whether negative values are allowed 


Work Product
In a normal data model, entities represent business concepts such as PURCHASE ORDER, EMPLOYEE, or PART. These entities have relationships with one another and they have attributes (i.e., data element definitions) describing their data content.
A data dictionary structure is similar except that the entities are system objects such as DATA ELEMENT, FILE, SCREEN, REPORT, RECORD, PROGRAM, or PROCESS. Sometimes these data dictionary entities are called meta-data entities or meta-entities.
These meta-entities have meta-relationships with one another (e.g., RECORD contains DATA ELEMENT, PROGRAM accesses RECORD, processes belong to PROGRAM). Common relationships include: 


File contains record. 
Record contains data element. 
Data element is used by report, screen, window, transaction, program, and module. Program uses file. 
Program generates report. 
Program contains module. 
System contains program. 
Program belongs to jobstream. 


A conceptual data model (CDM) of a data dictionary can be prepared showing meta-entities and meta-relationships in the same way as a data model can be prepared for a business process.



A data dictionary object (meta-entity) has meta-attributes (e.g., a DATA ELEMENT has the attributes NAME, SIZE, PRECISION, DESCRIPTION, and RANGE).
The structure of a data dictionary is defined in terms of these meta-entities, relationships, and attributes. The data dictionary stores multiple occurrences for each of these (e.g., SOCIAL SECURITY NUMBER is an occurrence of DATA ELEMENT with a SIZE of 11 and is contained in the RECORD named EMPLOYEE). Thus, the data dictionary would typically have a table for DATA ELEMENTS and another for RECORDs.
