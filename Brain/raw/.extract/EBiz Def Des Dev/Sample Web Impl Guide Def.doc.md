User Types and Needs

Overview
The end user identification and needs analysis process is the foundation activity of the site/marketing strategy development and influences the entire scope of the project. This analysis is built into a matrix designed to identify required content, tools and functionality and categorize users(s). The refinement of the matrix is an iterative process that takes place during the definition phase.  This matrix will also address high-level goals for personalization by identifying user activities.  In addition, the matrix format will support a visual re-organization of user segments, as proxies for BroadVision Communities, once the marketing managers have completed the template.

Approach
Determine user types by identifying all potential users visiting the site.  Once the user types have been outlined, we can then list high-level user wants and needs associated to each user type.  Consolidate user types list by identifying the commonality (similar wants and needs).  Determine the tasks that are necessary to fulfill associated wants and needs.
  
Work Product
The typical working document is prepared and managed in an MS Excel worksheet in a matrix form that provides for ease of manageability and organization.  Typical matrix organization column header’s are: End User Type, End User Needs, and Required Functionality by phase / importance.

Requirements Matrix

Overview
The requirements matrix captures and details all known system requirements. The matrix is composed of not only business/functional requirements, but also purely technical considerations.   This is a document that maps business objectives and capabilities to the technology capabilities that are needed to fulfill these objectives.  The types of information this document captures are intended as input to conversations related to scoping and release schedules.  Many of the considerations are captured in the priorities and complexities of each of the system requirements.


Approach
The approach to completing the requirements matrix is to list all the capabilities required of the system in order to enable the fulfillment of the business strategy.  These capabilities are initially identified through a review of the project business case or business strategy.  Further refinement of the capabilities occurs during the discovery and definition phases through use cases, content inventory, and analysis of the selected technology capabilities.  Input from all stakeholders (both business process and technical) is essential to complete the requirements matrix. 
.

  
Work Product
The typical working documents are prepared and managed in an MS Excel worksheet in a matrix form that provides for ease of manageability and organization.  Typical Matrix organization / column headers include BroadVision support, in-house support, 3rd party support, back office integration required, comments, questions/concerns, target release initiatives, requirement contact name.  

 
Input
Project business case or strategy documentation, use cases, content inventory, analysis of selected technology capabilities, and input from all stakeholders (both business process and technical).

Detailed Use Cases 

Overview
The goal of any system is to help the user get work done. The Use Case shows the interactions between the end users (actors) and the system as a basis for building the system capabilities that help the user to do his/her work. 
 
Approach
There are four steps in defining a Use Case:
Façade – outlines the use case and describes it at a high level
Filled – broadens and adds detail
Focused – narrows and removes extraneous information
Finished – touches up and tunes the Use Case
Each of these steps is described in more detail below.
  
Work Products
The following industry standard UML Diagram Tools are used to define a system:
Use Case List
Use Case Diagrams (optional)
Use Case Template
Business Rules Catalog
Use Case Context Matrix
 
Façade
At this step, placeholders for each major interaction users expect to have with the site are provided.  At this point, the initial list of potential Use Cases should be drafted.  At a minimum, the following fields in the template for each Use Case should be completed:
Actors Use Role Name
Use Case Name
Summary of the goals the Use Case accomplishes
Initial Business Rules Catalog list of rules that constrain the construction of the Use Case
 
Filled
This is the major step in defining the Use Cases. At this step, a comprehensive set of Use Cases along with the business rules that describe the solution are defined. The following tasks should be completed:
Identify detailed Use Cases. 
Evaluate the level of granularity of each Use Case to ensure that the Use Case is manageable. The result will be a hierarchical breakout of the initial Use Case list. 
Complete the Use Case template for each Use Case. 
Identify nonfunctional requirements (e.g. Security).
Add and document any new business rules in the Business Rules Catalog.
 
Focused
This iteration narrows the scope of each Use Case and removes duplicate information. The following tasks should be completed:
Identify the scope of the use case feature set.
Further prioritize features.
Remove duplicates.
Create a content matrix to show the dependencies between the Use Cases. This helps to identify situations where removing a specific Use Case would make a remaining Use Case unusable. The following table shows a sample Context Matrix.
 
Finished
The final step is to touch up and tune the interface. The following tasks should be completed:
Add user interface requirements to use case model.
Combine nonfunctional requirements with functional use cases.
Create baseline requirements.
Generate wire frames from these use cases.

Functional Storyboards

Overview
Functional storyboards are used to prototype how a site behaves by looking at the section of the site and modeling its functionality down to the page level.  More than a simple wire frame outline of page elements, a functional storyboard details how each page functions under different conditions.  While the functional storyboards are not intended to show layout and design, they are helpful in addressing high-level interface and usability issues.
 
Approach
Once the dynamic web page templates are identified, the business team focuses on creating 'functional storyboards' for only the personalized dynamic templates by associating use case functionality at the page level.
Identify the user goals each section addresses.
Model the tasks necessary to complete these goals.
Remove any unnecessary tasks.  Keeping in mind that less is more.
Create storyboards for each page in the process.
Clarify the specific purpose of the page.
Inventory the elements that make up the page.
Organize the elements into a logical interface.
Simplify the storyboard to improve understanding.
Assess the effectiveness of the storyboard.
  
Work Product
A functional storyboard is typically a rough MS PowerPoint mock-up of the web page layout, with no attempt to define colors, images or a 'user experience'.

Relationship Architecture
Overview
The Relationship Architecture is key to planning the personalization strategy for the web site.  It is used to begin to understand how to ‘treat different site users differently by conducting a needs analysis by high level community. The Relationship Architecture helps the team to understand how to ‘push’ content (products, ads, and editorials) to different types of site visitors. It is also the foundation for starting the content inventory, further understanding business requirements, validating segmentation strategies, mapping products and content to communities as a basis for business rule development.
 
Approach
The approach to the Relationship Architecture analysis is an understanding of all site users (communities) and the segmentation strategy.  Site users should be grouped into ‘high-level’ communities (to the extent this is applicable) which are mutually exclusive, and collectively exhaustive.  [The template example includes a lifestage segmentation strategy with the following high-level communities:  student, young professional, family, retiree].
 

Work Product
A Relationship Architecture template should be completed for each high level community.  The team should have a thorough understanding of the scope of products and content available for the site (or what is desired, but realistic).  Template completion is typically an iterative process. Once the templates are completed, items can be prioritized based on a phased release strategy. 


High Level Communities
High level communities are useful because they enable:
Relevant default content in the case of an anonymous or not-yet profiled user
A recommendation agent of content and/or products
Synonymous user or ‘assumed persona’ strategies
Entitlements on a knowledge site
Thinking through business rules strategies
 Some overlap in high level communities is permitted provided that it does not confuse the site visitor.  Completing the Relationship Architecture helps the project team to identify the ‘slice’ of the site content, which is most relevant to the high-level community.

Completing the Relationship Architecture
To complete the Relationship Architecture, it is useful to imagine that you are a member of a single community coming to the site. Answer the question:  what  products, editorial content, and site functionality do I need (or what is most relevant) as a member of that user community?   Brainstorm ideas and be very detailed. If you find your Relationship Architecture includes a lot of repetition across communities, you either need to be more detailed enough or to define your high level communities more carefully.

You can also complete Relationship Architectures for some key sub-communities.  These are typically profile elements, which will be also be drivers for targeted content and entitlements.  Your sub-community Relationship Architectures may not be as lengthy as your high-level community Relationship Architectures. The template example includes sub-communities of [homeowners and net worth/value].

If you identify any elements/site functionality needed or relevant to all users, add this functionality to your general business requirements list.
 
Dependencies 
Input to the Relationship Architecture includes:
Site user analysis
Segmentation strategies
  
Results
The results of the Relationship Architecture are:
Validation of site users and segmentation strategies
Relationship Architecture for each High-level community and some key sub-communities
Potential additions to Requirements list
Input to the Functionality matrix
Input to the Content Inventory
  
Factors Affecting Start-up and Completion
The following factors affect start-up and completion of a successful Relationship Architecture:
A good understanding of customer’s segmentation strategy
Participation/input from customer’s product and content managers
Understanding of the availability of content or the reasonableness of obtaining content in time to publish to the site prior to the release
The ability to prioritize/make trade-offs of some additional business requirements which tend to surface during this analysis

ERM Classifiers and Qualifiers, Programs and Channels

Overview
Classifiers provide a way in which content administrators can manage a user’s access to content at a category/subcategory level.  Classifiers are a way of labeling groups of users.  The more classifiers a user belongs to, the more content the user can view on the site.  Qualifiers are used to further define/limit a user’s access to content.  As the number of qualifiers assigned to a user increases, the more focused the content served to them can become.  Channels and programs (categories and subcategories respectively) provide a similar grouping structure for the content. These groups of content are then managed by granting access to users who are identified by certain classifiers and qualifiers.  Channels distribute the right information quickly and easily to the right people.   The use of Classifiers and Channels provide a quick way to render content without the creation of extensive business rules.
 

Approach
Classifiers are based upon site user segmentation and the approach for that process is defined elsewhere.  The process for defining qualifiers is to identify how content will be used on the site to satisfy a particular user’s needs.  The qualifiers help to further define a user beyond the high-level segmentation group to which he/she belongs. This also may take into account the different business rules that will be implemented to ensure that the appropriate qualifiers are identified to satisfy these rules.
  
Work Product
The typical working document for capturing ERM classifiers and qualifiers is an Excel spreadsheet of user segments.
 
Input
Completed use cases, content categorization and client personnel who are familiar with existing content and site personalization strategy.

Content Inventory, User Content Needs and Gap Analysis

Overview
The content inventory, user content needs and gap analysis process is the foundation activity of identifying the content that will fulfill the site/marketing strategy development needs for the entire project.  This analysis is built in two cross-referenced matrices defined to identify the current existing content inventory and user content needs, and mapping them against each other to determine additional content which needs to be developed to meet the site user needs.   The matrix is refined throughout the definition phase and also eventually will identify content owners, sources (internal or external) and content migration issues.  The organization of this complete content inventory will support the identification of the initial content categories and subcategories to define the content hierarchy.

Approach
The approach to determine the content inventory is to identify through existing documentation and/or user meetings content items currently utilized in the organization.  The approach to determine the user content needs is to identify through existing project documentation and/or user meetings the content required to fulfill the business objectives/vision for the site.  The gap analysis is the comparison of these two documents to determine what content needs cannot be met through existing content.
  
Work Product
The typical working documents are prepared and managed in an MS Excel worksheet in a matrix form that provides for ease of manageability and organization.  Typical Matrix organization / column headers for the Content Inventory are; Primary Content Category, Page or Content Item, Description, Owner, File Types, Migration Issues, Internal/External and Number of Items.  Typical Matrix organization / column headers for the User Content Needs are; Content Need ID, Primary Content Category, Page or Content Item, Description, Approximate Number of Items Needed, Expected Source, Expected Owner, and Content Type (static files, dynamic DB / personalized, or application / functionality), Existing Today.
 
Input
Existing content documentation and client personnel who are familiar with existing content and site personalization strategy.

Content Migration Issues

Overview
The content migration issues identify the potential steps required to migrate content from the current content environment into the BroadVision system.  This analysis is performed after the content inventory and user content needs exercise.  The information is identified simply as an additional column header on the content inventory matrix.  Migration issues are identified on an item-by-item basis.  
  

Approach
The approach to obtaining content migration issues is primarily achieved through working through the content inventory and identifying the different types of content that need to be integrated into the BroadVision system.  Different types of content may require varying levels of integration effort.  This can include external content feeds, existing static content, existing dynamic content, etc.    
  
Work Product
The typical working document is prepared and managed in an MS Excel worksheet in a matrix form that provides for ease of manageability and organization.  The content migration issues are identified with a “migration issues” column header.

Content Categories and Subcategories

Overview
Initial content categories and subcategories identify how content will be organized at the highest level.  This analysis is performed after the user content needs analysis.  The analysis is the logical grouping of the existing content needs and this categorization will serve as a basis for the complete content hierarchy.  
 

Approach
The approach to obtaining the initial content categories and subcategories is to work through the user content needs list and to “bucketize” or group related needs into logical categories.  Doing this should also take into account how rules will be targeted and implemented against content.

The approach to obtaining the initial content categories and subcategories as a rule should generally utilize the BroadVision out-of-the-box content categories (editorials, products, advertisements, etc.) unless special access rights are needed to utilize the One-To-One Command Center.

  
Work Product
The typical working document is a reworked user content needs list prepared and managed in an MS Excel worksheet in a matrix form that provides for ease of manageability and organization.  The user content needs list will be organized by content categories and subcategories.    
 
Input
Completed user content needs and client personnel who are familiar with existing content.

Content Attributes

Overview
Initial content attributes provide information about content that help determine its relevancy to a user.  This information, or meta-data, are descriptors of content and can include data information (creation date, start date, end date, title, text, etc.) and matching information (industry, segment, etc.).  This information is used to identify content records so that they may be dynamically served to a user based on the matching of a business rule against the content attribute(s).
 

Approach
The approach to obtaining initial content attributes is to identify how content will be used on the site to satisfy particular user’s needs.  Doing this should also take into account the different ways content will be served throughout the site.  This also may take into account the different business rules that will be implemented to ensure that the appropriate attributes are identified to satisfy these rules.

  
Work Product
The typical working documents are matrices based on content type (editorial, products, advertisements) that break out attributes for each content category and subcategory as identified in the content categorization.  This document is prepared and managed in an MS Excel worksheet in a matrix form that provides for ease of manageability and organization.  Typical column headers include content category, subcategories, attributes and related attributes.
 
Input
Completed content categorization and client personnel who are familiar with existing content and site personalization strategy.

Current Organizational Structure

Overview
A new web technology will normally have an impact on the structure of the organization.  As process changes are defined for maintaining dynamic personalized content, new roles and responsibilities are identified, information on the impact to the organization structure must be gathered.  An assessment of the current structure must occur.   

Approach
The approach to identifying the current structure requires three steps. First, locate and collect all current organizational charts. Next, identify and define all reporting relationships within the organization. Finally, define completely all job descriptions within the organization.

  
Work Product
The typical working document will be an organization chart indicating the relationships between divisions, units, groups, and/or individuals. This document is prepared and managed in either of the following: MS Excel worksheet, MS PowerPoint, or Visio. Also, textual information describing the relationships between various units can either appear on this chart or when extensive detail is available in an MS Excel or MS Word document. In the case of extensive detail, typical column headers that identify the information include entity x, entity y, relationship type, and relationship description. Finally, all job descriptions can be prepared and managed in MS Word or MS Excel. Typical column headers that identify the information are job title, tasks, output, tools required, skills required, performance measures, etc.

Organization charts and information provided by personnel familiar with the organizational structure.
