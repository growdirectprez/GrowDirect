Develop Publishing Workflows

Overview
Developing publishing workflows is the process of integrating the designed authors, roles and workflow into the Publishing Center so that site content can be created, tagged, approved and published by the appropriate authors within the BroadVision system.  
 

Approach
The approach to developing publishing workflows is to build the process identified to create, tag and approve content within the organization into the Publishing Center.  After the workflows are developed, the workflows are mapped to the Instant Publisher Forms which represent the appropriate corresponding categories of content (articles, products, etc...).  Additionally, inboxes and access groups are created to correspond to the authors and roles identified in the design phase so that these individuals and/or groups of individuals can participate in the workflow process as designated in the design phase.     

  
Work Product
The typical work product is the integration of all publishing workflows, authors and roles into the Publishing Center so that content can be published within the BroadVision system.      
 
Input
Required inputs are the finalized design of authors, roles and workflows.

Develop Instant Publisher Forms
Overview
Developing Instant Publisher Forms is the process of building the content management templates used to create, tag and submit content with the appropriate attributes into the BroadVision system.  

Approach
The approach to developing Instant Publisher Forms is first to finalize, review, validate and sign-off the template mock-ups for each distinct attribute set created in the design phase.  After the template mock-ups receive final approval, the templates are developed.  Each attribute becomes a field that content creators and editors use to create, tag and submit content.  Depending on attribute value, these fields can be text fields, radio buttons, drop-down boxes, etc. to facilitate efficient and consistent content publishing.   After the forms are developed, they are assigned to corresponding workflows.

  
Work Product
The work products are completed Instant Publisher Forms that, when assigned to appropriate content categories and workflows, and are integrated into the Publishing Center, can be used to create, tag, edit and submit content into the BroadVision system.     
 
Input
Required input for development includes designed content categorization, content attributes and authors, roles and workflows.

Implement Third Party Tools in BroadVision Environment
Overview
The Third Party tools are defined as content components that perform certain utility functions, and have been developed independently of the client’s efforts.  Such tools could include:

Loan Calculators
Account Selectors
Specific Forms and Templates

These tools would have to be integrated with BroadVision environment and its existing content components.  Many times, these tools reside as their own content type.

Approach
The approach the development team takes to implement third party tools in the BroadVision environment is to first analyze the different third party tools and convert them to a BroadVision compatible scripting language (i.e. Java Script).  The team must also identify what content is needed to be passed on to these tools and arrange for such input.

The team then migrates the converted scripting pages/windows to the required server.   Depending on the number of tools being integrated into the site, a specific content type and/or content category for Third Party Tools might be created in the Command Center.  The team also will assign additional information about the tools (attributes), such as URL address, file name, description in the BroadVision Command Center.

Depending on the site architecture and personalization strategy, business rules might be written in the Command Center to support the delivery of Third Party Tools to site users.

Once finished, web page developers should be able to evoke these tools by simply referring to a specific content category and specific attribute that is required (i.e. link name, URL address, description, etc.).
  
Work Product
The resulting work product of the Third Party Tools integration is a new category in BroadVision Command Center that contains the records and related attributes for the required tools.  


 
Input
The original scripts/executables for Third Party Tools, as provided by vendors or other teams and business units, serve as input for integration process.

Develop Data Model 
Overview
The data model defines the One-To-One database that contains the data to be used within the BroadVision system.  This data model is also known as the database schema and serves as the “map” of the One-To-One database.  It is this schema specification file that defines the tables, attributes (columns), and data types of the One-To-One database.  The file also:

Defines the group that determines which columns appear together in the Command Center.  
Defines the column names and tool-tip message that for each column in the Command Center.
May define data storage specification for the table (the amount of memory to reserve).

The file can be use to extend the definition of the visitor profile, and content tables, as well as to create new content types.

Approach
The approach used to develop the data model is to first define the schema specification file.  This file is a structured text file that describes the customized portion of the One-To-One database.  The One-To-One database uses an object-relational model.  This means that data is stored in the relational database, but are treated as objects by the program.  To accomplish the mapping from database to object, One-To-One uses meta-data tables to describe the One-To-One database.  To change a table’s structure, the specification file must be changed and then compiled into a schema file, then the changes in the schema can be applied to the table.  

Work Product
The typical working document is a schema requirement file, which is a structured text file that describes the One-To-One database in non-SQL term.  The text file can be edited by any text editor.  Typically, each file defines either one or more One-To-One database tables, or the extended data type that One-To-One recognizes. The file also lists each of the attributes of the table.
 
Input
Completed database tables inventory and client personnel who are familiar with the existing RDBMS architecture.

Load and Tag Content 
Overview
Loading and tagging content is the task of bulkloading content into the BroadVision system.  

ApproachThe approach taken to bulk load content into the One-to-One database, a text file/spreadsheet is built to map to the data model.   In this file, the necessary attributes are tagged with data to reflect the unique characteristics of each content record.   In the text file, the first line of the text file must be a CONTENT_TYPE directive that identifies the content type to receive the data, such as this example that loads ADVERTISEMENT data.

Following the CONTENT_TYPE directive is the row that identifies the attributes that will receive the data. The rest of the file either contains the data to load, or a DATA_FILE directive that identifies the text file that contains the data to load

Regardless of whether the data is in the same or a different file, each row of text is one row of data to load. The fields of data must appear in the same order as the attribute list. The only fields of data do not have to be in the file are OIDs, service IDs, creation time, and modification time columns.   These columns are created by the bv_load_content utility.   When you run this utility you must provide at least the name of the service that owns the content, and the name of the file that identifies the content. For example: 

       % bv_load_content -s "AthleteDirect" -f bv_advertisement.txt

This utility copies the data from the data file into the table, and creates OIDs, service IDs, creation time, and modification time columns. During the load it also fills in the fields for the new columns. 


Work Product
The work product is content that is fully loaded and tagged in the BroadVision Dynamic Command Center (DCC).
 
Input
A text file that contains contents that can be mapped to the backend data model.

Unit Test Batch/Interface/Data Migration Programs

Overview
Define the test objectives for the unit being tested. The purpose of unit testing is to thoroughly test the individual modules or set of related modules which execute the migration programs. Each objective is to test for a correct response to an event. For example, a unit test objective may be "to test that a migration program transferred account identification data correctly." Unit test objectives may be grouped into test cycles for execution purposes. 
 
Approach
Define Unit Test Objective
Prepare a Unit Test Strategy to document the unit test objectives and test cycles
Develop a Unit Test Plan where all conditions, steps to be executed to test each condition, required unit test data, and expected results of each step are defined
Establish unit test conditions to address the verification of the following: 
Output conditions (e.g., displays, reports, updates, error messages) 
Program logic paths, including loop control, exception, and/or error processing 
Edit/validation logic within the program, including table look-ups 
Error handling routines 
Processing algorithms 
Module to module interfaces within the program 
Use of program links 
Production of specified output files 
Reading of specified input files 
Control and security conditions 
Command language instructions for the program 
Utilities 
Unit test conditions describe the explicit scenarios which must be tested to meet the test objectives.
Define unit test steps for each test condition
Prepare Test Data Specifications
Generate Unit Test Data by developing test data files to enable the execution of all test conditions and steps defined in the unit test plan. 
Define expected results for each test step
Conduct unit tests until each test has been successfully completed. Actual results are reconciled with the expected results and all program logic errors are corrected. Final test results are attached to the unit test plan for each test condition/step. Successfully conducted unit test plans are reviewed by the team leader.
 

Work Product
Typical work products are test strategy template, test plan template, test data specification template, unit test plan, data analysis specifications, performance test plan, performance stress test.
