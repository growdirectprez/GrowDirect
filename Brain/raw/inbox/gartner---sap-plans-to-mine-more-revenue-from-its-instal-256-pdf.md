SAP Plans to Mine More Revenue From Its Installed Base

SAP is adding new categories to its pricing model and is
using its software license agreements more creatively to
generate further
revenue. Gartner answers important
questions from SAP clients about this strategy.

In the current economic climate,
revenue from business
application software is hard to find — even for leaders such as
SAP. SAP has introduced a number of new license categories for
2003 and is innovatively interpreting contractual clauses to obtain
more money from the smaller number of available deals. Clients
who plan to buy software from SAP in 2003 need to understand
the expanded SAP license model and the additional costs they
may incur.

Clients with SAP license agreements will remain unaffected —
until they need to renegotiate with SAP for more licenses or
redeploy existing ones, at which point they will be subject to the
2003 license model or strategy. Four major questions about
SAP's 2003 license strategy emerge:

1) Why do customers now have to pay for SAP application
interfaces?

When SAP first introduced its mySAP.com license model (now
called mySAP Business Suite), it tried to charge customers for
transactions triggered by automated interfaces, as well as by
named users (see Note 1). SAP had great difficulty in measuring
such interface transactions and its customers had even more
difficulty predicting the licensing fees.

In 2001, SAP abandoned the notion of charging for all
transactions and instead charged only for purchase order (PO),
and sales order (SO) transactions from automated interfaces
(where no users are involved). This was because these e-
commerce transactions represented real value for its customers,
but e-commerce never really developed as SAP had hoped. PO
and SO transactions are licensed according to annual order
volume (see Note 2).

In 2003, SAP has changed course again and customers now
have to pay for other interfaces with other applications, under
certain circumstances. The problem is that virtually all SAP R/3
systems have between 30 and 100 interfaces to other systems.
There has always been a latent, "catch all" clause in SAP's
standard agreement that states "Each access, direct or indirect,
needs to be licensed." In 2003, SAP now uses this clause
selectively to license some outgoing interfaces from SAP
applications as equivalent named users.

Problems with this approach are:

(cid:127) Organizations will

face unexpected and dramatically high
license fees — in many cases paying two software vendors
for the same users. For example, portals are a special case
of synchronous access to SAP applications. Organizations
planning to use a third-party alternative to SAP's Enterprise
Portal will also have to pay SAP named user license fees,
which will be high because of the large number of users
often involved. A further example would be if an organization
licensed Siebel Systems for a call center application and the
agents had to access data "indirectly" in a SAP financials
application, fees would be due to both SAP and Siebel for
the same users.

(cid:127) SAP has no rigorous technical definition for exactly which
outgoing interfaces fall
into this "indirect access" category.
The criteria used to evaluate whether interfacing fees will be
due include bidirectional, synchronous or asynchronous
transfer and frequency — although these do not appear in
contracts or any policy document. Rather, each case must
be interpreted by SAP's pricing director in Walldorf, Germany
on a one-off basis. This is a very unclear area and
unsatisfactory from the client perspective. Each case has
unpredictable costs and takes time to resolve.

SAP justifies this new approach by maintaining that some
organizations build an interfacing layer
to artificially reduce
license fees. By charging named user fees for indirect access to
data in SAP applications, it thinks it will recoup license fees, or
prevent this practice entirely. However, building SAP interface
applications is costly, and we believe very few organizations will
do this solely to avoid paying SAP for additional licenses.

It is both onerous and unreasonable for SAP to ask for additional
license fees for any non-SAP applications (for example, Siebel,
Oracle or legacy) that use data extracted from SAP applications.
In a heterogeneous world, organizations select non-SAP
applications for many reasons. Organizations should strike out
the phrase "or indirect" from the clause in the contract
that
stipulates that all "access, direct or indirect," should be paid for. It

There are two concerns with this approach:

(cid:127) In this scenario, SAP is confusing the use of a SAP
application with use of data that belongs to the organization

SAP application. At the very least, there should be absolutely no
charge for extracting data using non-SAP techniques and to
directly access BW info-cubes using tools from companies such

be licensed?

The traditional SAP R/3 license model — with its seven user
categories and based on intensity of application use — identified
a specific, named user category for developers of R/3

In 2003, SAP will further complicate its licensing model by adding

Organizations should identify all developers carefully, including
