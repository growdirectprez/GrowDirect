Allocation (Overall)
Objectives
To maximize customer satisfaction, sales, profitability and inventory productivity through the optimal distribution of merchandise.
Critical Success Factors
Ability to provide the right product to the right place at the right time.
Accurate perpetual inventory values.
Assumptions
Within the process (Maintain Item), create and delete is included.
Allocation is the push distribution method used outside of normal replenishment.
There are situations where allocation will not generate follow on documents immediately in 	order to be able to review allocation quantities before document generation.
Allocation will create external purchase orders or internal transfers.
Interface between SAP and EXE needs to be as real-time or as close as possible.
All listing requirements are handled in Assortment Management (Item Setup).  It will be required to list an article in a site assortment in order to allocate.
An SAP Terminal will be in each store.
Performance Measures
Overall Measures
Quantitative
Gross Margin Return on Investment (GMROI) (Actual $, planned $ and variance thereof)
Sales (Measured by comparing price/unit against Actual, Plan & variance thereof)
Turnover (Inventory/turnover against Actual, plan and variance thereof)
Sell through percentage - Both company wide and at site level.  (Compare to Standards)
Lost sales
Amount of residual inventory - Reported at organizational and merchandising hierarchy levels.
Service Levels
Qualitative
Customer Satisfaction
Overall Store feedback

Better Practices Recommendations
Purchase orders generated by allocation models are as follows:
Promotions
Events
One-time buys
A combination of pre and post distribution is used where:
Pre-distribution is utilized for initial distribution of goods for a new selling season.
Post distribution is utilized for replenishment based on current sales.
Specify allocations for either initial, backup, or sales replacement.
Manage allocation changes by exception as they are put up for review.
Integration occurs with store planning and space planning modules.
Allocations are constrained by:
Minimums which represent minimum presentation quantities at the store
Maximums which represent capacity levels.
Allocation models are based on:
Time supply (historical sales or forecast)
Target quantity needs
Store model quantity
Projected promotion/event sales and conditions
Schedule distributions for new and existing stores based on plan-o-gram and reserve store opening inventory shipments up to a specified number of weeks in advance.
Base allocations on like-items or like-promotions/events rather than department or class.
Allocation models are evaluated based on degree of utilization and effectiveness.
To fulfill emergency  requirements, the following manual transfers are available to merchants:
DC to store transfers
Store to store transfers
Store to DC transfers
Benefits of manual transfers are evaluated against the cost of the transfer.
Guidelines limiting manual transfers are established.

Existing SAP functionality
Assumptions
SAP is currently set up for normal instead of push replenishment.
Allocation rules consist of sites and distribution ratios.
Site groups consist of two types that are used in creating the rules and then applied to articles to create the Allocation Table
Fixed - Unchangeable - A snapshot in time of the group.  If sites are added after the rule is fixed they will not be recognized until the rule is reworked
Dynamic - Changeable - As sites are added to the group they will be recognized by allocation processing as soon as changes are committed to the group.
You can assign multiple site groups to a rule.  If a store exists in more than one site group that is assigned to a rule SAP will warn user that there is a conflict.  [If the user ignores the warning it’s possible that without correcting the group that the particular site belongs to that good may be mis-allocated. (e.g. If site #1 is in group A and is slated to get 25% of the goods for that group AND Site #1 is in group C and is slated to get 33% of the goods for that group then Site #1 will get the 25% AND the 33%) - Ralf is currently looking into as to whether this can be treated as a error, warning or informational message.]
Relevant Components of SAP
Retail Information System (RIS)
Definition - Module in SAP where PETsMART will build reports - both standardized and ad hoc.  there is good but somewhat limited capability in RIS - therefore the need for a data warehouse which will also drive reporting.
Functionality generally related to Allocation - PETsMART needs to create rules on performance which includes what SAP calls Key Figures (e.g. sales, stock, turnover).  Some of the figures are can be accessed for query and rules creation (like sales, stock).  Some figures we want to access (e.g. forecasted sales of a like item) cannot be accessed.  This is because SAP has chosen not to maintain forecasting as a key figure and therefore is not accessible through an existing SAP infostructure. The RIS gives PETsMART access to the key figures PETsMART can use (Recall that PETsMART wants to use more than what SAP offers access to), and the creation of the reports/tools resides in the RIS.
Functionality specifically related to Allocation - PETsMART can pull other data  (e.g. the result of a calculation from the data in the data warehouse) and use it to derive an allocation rule.  This is called a “user exit” by SAP.  The user exits need to be written and SAP concedes that this may be a somewhat complicated task - all depending on the type and amount of data we need to access.

Ability to apply more than one arithmetic operation to multiple key figures within a single infostructure.  Currently all figures within an infostructure must be subjected to the same arithmetic operation.  (e.g. You cannot use the SUM [] of inventory and the Average of sales.){80}  Example:  A common method of allocating inventory is to base the allocation on each site's current "weeks of supply" of inventory.  "Weeks of supply" is defined as available inventory divided by average weekly sales.  In this case, you may want an "ending inventory" balance key figure and a "weekly sales quantity" key figure in an infostructure where the data is stored by article, site and week.  You would need the ability to calculate an average of the weekly sales figure (for a user-defined number of weeks) and divide the current inventory balance by this average to determine each site's weeks of supply number.  The weeks of supply number for each site would then be used to calculate the allocation percentage for each site.
