Consumer Demand Detection Algorithm

The Consumer Demand Signal Service relies on the Data Ventures' XPLOSS algorithms to learn normal item velocities and detect statistical variances from these such as "moving too fast", "moving to slow", "new item", "dropped item", and out-of-stock (OOS).  XPLOSS learns best from minute-by-minute transaction data containing the details of what items were observed and at what price for every transaction.  In the supermarket context, a transaction is a "shopping basket checkout", and observations are UPCs or item codes scanned by the checker.  For every transaction, the data includes at least a time stamp, a series of items identified by UPCs or item codes, the item quantities, and the net price of each item or the regular price plus applicable discounts.

Training of the XPLOSS algorithm yields a model of item velocity for each monitored item at each monitored store under various merchandising conditions.  The XPLOSS algorithm does this by transforming historical item movement data (across 1 or more stores) into a series of "event observations" whose arrival times behave in a random, statistically independent way called a Poisson process.  The details of this transformation are proprietary and confidential to Data Ventures and P&G.  The XPLOSS model accounts for current price, time of day and day of week, store name and current store traffic,  current promotions, in-store competition, and seasonality.  When the model is first trained, it is used to detect OOS, new item, and dropped item events.  These events are then used to "adjust" the historical data, which the model retrains to improve its accuracy. The model is automatically rebuilt every 15 minutes to 24 hours, depending on the specific installation.  

New transaction data is fed to the XPLOSS model to answer the question "What is the probability of the newly observed transaction data given the normal velocity model?"  (Note that "normal velocity" takes into account current conditions such as price, promotion, traffic, etc.)  If there is a small probability of the data being what it is or more extreme (e.g., slower/faster sales), then an anomaly event is generated.  The kind of event (new item, dropped item, OOS, fast, slow) depends on the transaction data and model rules.  These rules are adapted for specific installations.  Events are immediately stored into the events cache so they can be accessed by the events server.  Certain velocity model details, such as expected item velocities and historical item sales are put into the cache as well.

The item movement, velocity, and event cache contents can be accessed at any time via a client connection to the cache server.  These connections are currently made by either an XML or HTML client.  The server supports detailed reporting (e.g., individual events or item velocities, most recent item sale) and summarization (e.g., service level over the past month, current OOS event losses exceed some threshold, observed item velocity over the past day).  The cache is normally updated every 15 minutes.

The DV/P&G  Item Velocity Monitor consists of:

  • a data feed (for trickled TLOGs and daily Item Tables)
  • data handlers (RCO, POS_DATASOURCE, XPDATAREADER, XPIVMDBWRITE),
  • a high-speed, compressed transaction database (XPDB, XPSORT),
  • a velocity monitoring and out-of-stock (OOS) detection algorithm (XPLOSS),
  • an item movement and velocity/OOS events cache and server (IVMSERVER),
  • a web server (http daemon)
  • an HTML events formatter (CGI bin IVMCLIENT)
  • an XML events formatter (notification client IVMALERT)
  • a processing scheduler (cron)
  • a batch process script (IVMDRIVER)
  • a messaging server (BizTalk)
