2. Vision: Digital Warfare, Not Security Guards

2.1 The Paradigm Shift

The legacy LP world (represented by the BRD) is boots-on-the-ground police work — physical apprehensions, supervisor interviews in back rooms, handwritten incident reports, CCTV tape reviews, and filing cabinets of case folders. That world still exists and Fox supports it. But Fox's real power is in what comes next: digital private investigation.

Fox combines:

  • Old school LP (incidents, interviews, evidence, prosecution) — simplified for a store manager who has 5 minutes, not 50
  • Digital forensics (device fingerprints, card fingerprints, CVV/AVS failures, transaction velocity, risk evaluations) — signals the old guard never had access to
  • Network intelligence (cross-merchant BOLO alerts, proximity notifications, shared subject profiles) — the "neighborhood watch" for Square merchants
  • Automated case creation — Canary and Owl detect, Fox auto-opens the case with evidence pre-attached

3. Data Model: The Unified Entity Map

3.1 Design Principles

  1. Immutable evidence chain — case_evidence, evidence_access_log, case_timeline are INSERT-ONLY. No UPDATE, no DELETE. Ever.
  2. Hash verification — SHA-256 file hashes on all evidence. Hash-chained audit log (Tom's existing pattern).
  3. Multi-tenant RLS — merchant_id on every table, Row-Level Security enforced (Tom's existing pattern).
  4. Soft-delete for operational entities — cases, subjects, locations use deleted_at timestamps.
  5. Hard immutability for evidentiary entities — anything that could be presented in court is INSERT-only.
  6. Standard entity pattern — created_at, updated_at, created_by, modified_by on all tables (Tom's pattern).
  7. 3NF normalization with JSONB extension fields for flexibility (Tom's hybrid approach).
  8. Square-first — entities optimized for Square POS data flow, not generic enterprise POS.

5. The Incident Report Form

5.1 Design Philosophy

A store manager just caught someone. They're stressed, their adrenaline is pumping, they might have customers watching. The form needs to be completable in 60 seconds for the basics, with the ability to add detail later. Not a 50-field enterprise form. A fast capture.

5.2 Form Fields (MVP — Sprint 1)

Auto-populated from Square/Canary

  • Store location (from merchant session)
  • Date/Time (NOW by default, editable)
  • Case number (auto-generated)
  • Employee on shift (from Square team_member data)
  • Triggering alert ID (if auto-created)

Quick Capture (Required)

  • What happened? (free text, 2-3 sentences)
  • Incident class: [External | Internal | Incident | Critical] (radio buttons)
  • Incident type: (dropdown filtered by class — 5-8 options per class, not 60)
  • Estimated loss: $ amount (quick entry)

Subject Info (Optional at Creation, Add Later)

  • Name (if known)
  • Physical description (free text)
  • Photo upload (camera button — tap to take photo)

Evidence (Drag and Drop)

  • Upload zone for photos, receipts, screenshots
  • Auto-attached: transaction log from triggering alert

One-Tap Actions

  • [ ] Report to police
  • [ ] Issue trespass notice
  • [ ] Escalate to manager
  • [ ] BOLO alert to network

6. Digital Forensic Integration

6.1 How Fox Connects to the JSONB Payload

Every case auto-created from a Canary alert carries the digital forensic fields from the transaction:

Fox Case Field Square Payload Source Investigation Use
device_id payment.device_details.device_id Which terminal — verify it was an authorized device
card_fingerprint payment.card_details.card.fingerprint Track same card across incidents without PCI scope
risk_level payment.risk_evaluation.risk_level Square's own fraud assessment — corroborate our alert
is_offline payment.is_offline_payment Offline = bypassed real-time controls
cvv_status payment.card_details.cvv_status Failed CVV with approved payment = red flag
avs_status payment.card_details.avs_status Failed AVS with approved payment = red flag
card_prepaid_type payment.card_details.card.prepaid_type Prepaid = organized crime tool
entry_method payment.card_details.entry_method KEYED = manual entry bypass
square_product payment.application_details.square_product Which Square app — channel anomaly

6.2 Automated BOLO Matching

When a BOLO is active, the system continuously monitors incoming transactions for:

  • card_fingerprint match against BOLO subject's known fingerprints
  • device_id match against BOLO subject's known devices
  • Geolocation match (transaction location within BOLO radius)

Match triggers auto-creation of bolo_sightings record with match_confidence score.

7. Network Intelligence: The Fox Network

7.1 Concept

Think of it as "Ring Neighbors for Square merchants." Merchants opt into geographic or affinity-based networks (shopping center, downtown district, franchise group). When one merchant issues a BOLO, nearby merchants get notified. When a BOLO subject's card fingerprint appears at another network merchant, a sighting is auto-logged.

7.2 Privacy Controls

This is sensitive data. Privacy controls are non-negotiable:

  • Opt-in only — merchants must explicitly join a network
  • Granular sharing — choose what to share (BOLO, photos, incident types, loss amounts)
  • Anonymized by default — network feed shows incident types and descriptions, not merchant identity
  • Subject data is network-scoped — a BOLO subject's profile is visible only to network members, not globally
  • GDPR/CCPA compliance — subjects can request deletion of their data (but evidentiary records preserved per legal hold)
  • No racial profiling — physical description fields are for identification, not profiling. System does not generate alerts based on demographics.

7.3 Partnership Model: ALTO Integration

ALTO (alto.us) connects crime incidents to legal outcomes. Fox provides the digital platform ALTO's physical LP teams need:

  • ALTO creates a merchant_network for their managed clients (e.g., "Dolphin Mall LP Alliance")
  • ALTO investigators get a multi-tenant Fox dashboard showing all client cases
  • BOLO alerts flow to all merchants in the managed network
  • Evidence packages export in a format ALTO can hand to law enforcement
  • API integration for ALTO's existing workflows

This is how Canary reaches the LP service provider market without building a sales force. ALTO brings the clients, Fox provides the platform.

8. Integration Architecture

How Fox connects to every other Canary module:

[Square POS] ↓ webhook [Canary Core] ↓ alert [Fox: Auto-create case] ↓ [Owl: Threat score] → [Fox: Update subject risk] ↓ [Fox: Evidence locker] ↓ export [PDF for police] ↓ [Fox Network] ↓ BOLO broadcast [Nearby merchants] ↓ [Fox: Card fingerprint match] ↓ auto-sighting [BOLO sighting recorded] Data Flow: • Square transactions flow through Canary's webhook ingestion • Canary detects fraud patterns and creates alerts • Alerts trigger auto-case creation in Fox (Sprint 1) • Investigators add evidence, interviews, police info (Sprint 2) • Narratives auto-populate for law enforcement (Sprint 3) • BOLO alerts broadcast to merchant network (Sprint 4) • Automated matching closes the feedback loop

API Integration Points (Jeremy's Scope)

  • Canary → Fox: Alert webhook triggers case creation. Transaction data with JSONB fields attached as evidence.
  • Fox → Owl: Case subjects queried for threat scores. Score updates case risk_level.

  • Fox → S3: Evidence storage. Server-side file hashing. Presigned download URLs.
