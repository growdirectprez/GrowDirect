Three Generations of the Same Pattern

The Canary Retail Data Model (CRDM) represents the third evolution of a unified data architecture for retail loss prevention — refined across three decades of enterprise implementations and hundreds of billions of processed transactions.

Generation 1: Till Data Store (TDS)

Built for a major UK department store chain in the 1990s. TDS captured point-of-sale transactions at the granular level: tender types, cashier actions, item-level lineage, and exception events. This was the foundation — proving that centralized transaction normalization could support pattern detection at scale.

Generation 2: SMART System

Deployed across thousands of retail locations internationally (2004–2016). The SMART system extended TDS principles with real-time transaction ingestion (RTI) — the ancestor of today's webhook listeners. It added multi-tenant isolation, role-based case management, and the first standardized "Chirp" alert taxonomy. Processed transactions across major international retailers.

Generation 3: CRDM for Square SMB

Canary's CRDM adapts enterprise patterns to the Square ecosystem. Instead of large proprietary till systems, we ingest POS data via Square's OAuth webhooks. Instead of a single retailer, we serve thousands of SMB merchants. The architectural DNA remains: normalized transaction schema, multi-source correlation, pattern rules, immutable audit trails.

The Constant: "Hundreds of billions of rows processed" — same detection logic, three different deployment eras. CRDM is proven technology at scale.

Data Flow Between Databases

Webhook → canary_sales (JSONB): All incoming Square webhook payloads are archived in append-only tables. No UPDATE, no DELETE. Evidence integrity is maintained.

canary_sales → canary_app (normalized): Extraction and parsing happens in Python. Fields are exploded from JSONB into normalized columns in canary_app tables. This separation allows schema evolution without breaking extraction logic.

canary_app → canary_metrics (aggregated): Nightly batch jobs materialize views into the metrics database. Merchant dashboards query pre-computed facts, not raw transactions. Fast response times, controlled costs.

Six Design Patterns

CRDM architecture relies on six proven patterns for scalability, security, and maintainability.

1. Multi-Tenant RLS
Row-Level Security policies ensure merchants see only their data. Implemented at PostgreSQL layer, not application layer.
CREATE POLICY merchant_isolation ON transactions USING (merchant_id = current_setting('app.merchant_id')::uuid);
2. Standard Entity Fields
Every table includes: id (UUID), created_at, updated_at, db_status (active/soft-delete), db_effective_from/to (SCD Type 2).
id uuid PRIMARY KEY, created_at timestamp DEFAULT now(), updated_at timestamp DEFAULT now(), db_status varchar(20) DEFAULT 'active', db_effective_from date DEFAULT CURRENT_DATE, db_effective_to date DEFAULT '9999-12-31'
3. JSONB + Extracted Columns
Raw payload stored as JSONB in canary_sales (immutable). Parsed fields extracted into canary_app columns (queryable, indexed). Schema drift captured in separate log.
-- canary_sales (immutable) webhook_payload jsonb -- canary_app (queryable) device_id uuid, risk_level varchar(20), cvv_result varchar(20) -- generated from webhook_payload
4. Hash Chain (Audit Integrity)
Every audit log entry includes SHA-256 hash of previous entry. Creates tamper-proof chain of custody for evidence tables.
INSERT INTO audit_logs (action, entity_id, user_id, previous_hash, current_hash) VALUES ('UPDATE case_1', 'case_1', 'usr_123', '5a3f2b...', SHA256(concat(action, user_id, ...)))
5. Monthly Partitioning
Large fact tables (webhook_events, transactions, refunds) partitioned by YEAR-MONTH. Enables parallel query, efficient archival, compliance holds.
CREATE TABLE webhook_events_2026_02 PARTITION OF webhook_events FOR VALUES FROM ('2026-02-01') TO ('2026-03-01')
6. Merchant-First Indexing
Every query includes merchant_id in WHERE clause. Indexes are designed as (merchant_id, timestamp, entity_id) for maximum cardinality and cache hit ratio.
CREATE INDEX idx_transactions_merchant_time ON transactions (merchant_id, created_at DESC, device_id, employee_id) WHERE db_status = 'active'

Transaction to Case Data Flow

A transaction's journey through Canary: from Square webhook to loss prevention case. 14 steps, multiple databases, immutable audit trail.

Square Webhook Received — Payment event from Square with full payload (JSONB). Timestamp synchronized with Square's event_created_at.
↓
HMAC Signature Verification — canary_sales webhook_signature verified against Canary's registered Square app secret. Unsigned events rejected.
↓
Raw Payload Archived — Webhook event inserted into canary_sales.webhook_events (append-only, JSONB). Entry hash recorded for chain-of-custody.
↓
Schema Drift Detection — Python fingerprinter scans JSONB against known Square API schema. New fields logged to schema_drift_log for monitoring.
↓
Field Extraction & Parsing — Python parser (square_client.py parse_payment_to_transaction v2) extracts 22+ fields from JSONB into normalized columns.
↓
Merchant RLS Context Set — Session-level app.merchant_id variable set to transaction's merchant_id for all downstream queries.
↓
Transaction Record Inserted — Normalized transaction inserted into canary_sales.transactions + canary_app.transactions. Device fingerprint created/updated.
↓
Risk Signal Evaluation — CVV/AVS/3DS flags evaluated and stored in canary_sales.risk_signals. Card velocity counters incremented.
↓
Chirp Rules Evaluated (Real-Time) — All 37 Chirp rules execute in parallel. Matched rules generate alert events with HIGH/MEDIUM/CRITICAL severity.
↓
Alerts Stored & Notification Triggered — Matched alerts inserted into cases.chirp_alerts. Merchant notified via webhook (async, Fire-and-Forget).
↓
Metrics Updated — Nightly batch job aggregates daily_sales_fact, employee_performance_fact, chirp_alert_fact in canary_metrics.
↓
Case Auto-Created (if Alert Critical) — CRITICAL alerts auto-escalate to Fox case management. Case status set to 'open', assigned to store manager.
↓
Evidence Chain Established — Fox case linked to transaction record. Evidence table (INSERT-only) records investigator actions, notes, hash-chain verified.
↓
Case Resolution & Audit Log Close — Case disposition recorded (fraud/error/verified). Audit entry hash-chained. Data locked for compliance hold if needed.
