Single Transaction Lifecycle — Event Journey

Webhook to Bitcoin Inscription — Complete Data Flow
FIG. 2 — Temporal Sequence (T+0ms → T+11min)
Phase 0
Event Generation & Transmission
Source network generates transaction event (UUID + ISO 8601 timestamp). Payload signed with HMAC-SHA256 using pre-shared merchant secret key. Transmitted as webhook POST to API gateway endpoint.
HMAC-SHA256(payload, merchant_secret_key) → signature header
T+0ms
Phase 1
Inbound Validation & Queue Publish
API gateway validates HMAC signature (rejects if invalid → 403). Computes SHA-256 hash of raw payload bytes. Assigns unique event ID. Publishes to durable message queue with fan-out to three independent subscribers. Returns 200 OK to source within milliseconds.
SHA-256(raw_payload_bytes) → event_hash
T+5ms
Phase 2
Triple Subscriber Fan-Out (Parallel)
Three independent consumers process simultaneously:
Sub 1 (Hash & Seal): Computes chain link (SHA-256 of prev_hash + current hash), writes to evidence store. Append-only, write-once. Bilateral verification: hash compared against source send log.
Sub 2 (Parse & Route): Extracts structured fields, writes to queryable partition. Emits to detection engine for rule evaluation.
Sub 3 (Merkle Batch): Accumulates hash into batch. When threshold reached, builds Merkle tree.
chain_hash = SHA-256(prev_chain_hash + event_hash)
T+15ms — T+50ms
Phase 3
Detection & Alert + Queryable Evidence
Detection engine evaluates rules against parsed event data (amount thresholds, velocity checks, pattern matching). Fires alerts to merchant dashboard via WebSocket. Structured store serves queries for reporting and analytics. Evidence store serves bilateral verification requests.
T+100ms
Phase 4
Merkle Aggregation & Bitcoin Inscription
Merkle batcher constructs tree from accumulated hashes. Computes Merkle root. Signs inscription transaction with custodied ECDSA key. Broadcasts to Bitcoin network. Ordinal inscription created on satoshi. Inscription ID and Merkle proof paths recorded in pool registry. Each individual event verifiable via its unique Merkle proof path.
ECDSA sign → Ordinal inscription (Merkle root) → Bitcoin block confirmation
T+~10min (1 block)
Phase 5
Perpetual Validation (L402 Sat-Gated)
Any party requests validation via API. System returns HTTP 402 with Lightning invoice. Upon sat payment: returns verification status, Bitcoin block number, Merkle proof path, inscription ID, and timestamp. Revenue generated on every validation call, in perpetuity, for every event ever notarized.
L402: Lightning invoice → sat payment → validation response + Merkle proof
T+∞ (perpetual)
