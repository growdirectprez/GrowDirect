## 1.1 The tLog Problem

**What IBM got right and what it couldn't fix.**

*Status: 🟡 Partial. Source: PhD `tLogToGlog_FounderCase_v1.0.md`. Needs Jeffe review and B-056 evidence (IBM emails, Palisades photos) before War Chest-ready.*

The IBM 4690 point-of-sale operating system introduced the tLog — a transaction log that recorded every POS event in sequence. For its time, it was remarkable: a complete, ordered record of everything that happened at a register.

The tLog had one flaw that IBM understood and could not solve within the architecture of the era: it was a mutable file on a server that the store controlled. The log recorded what happened. It did not prevent anyone with access from changing what was recorded. The record existed. The record could be argued with.

Every loss prevention system built on top of the tLog — and every system built after it — inherited this fundamental limitation. The data is only as trustworthy as the institution that holds it. The institution that holds it has every incentive to edit it when inconvenient.

Jeffe spent years working inside this system. He knew what it could prove. He knew what it couldn't.

## 3.4 The gLog

**Permanent event record on the Bitcoin time chain.**

*Status: ✅ Written. Source: PhD `tLogToGlog_FounderCase_v1.0.md` + ElJeffe Business Model Addendum. War Chest source: `02-eljeffe.html`.*

The gLog is the answer to the tLog's unanswerable question: how do you prove what happened, to anyone, forever, without asking anyone to trust you?

Every webhook event received from any network — Square, Epic MyChart, FedEx, any source — is hashed on INSERT. Periodically, accumulated event hashes for each merchant are assembled into a Merkle tree. The 32-byte Merkle root is inscribed on Bitcoin L1 via Ordinals. The inscription ID, block height, and Merkle root are stored in the anchor receipt, appended to the hash chain.

The result: every event ever processed through elJeffe is verifiable by anyone, against a public permanent record that GrowDirect does not control and cannot alter. Not "Canary says this is what happened." The block says what happened. The block is math.

The gLog is not a Layer 2 solution. It is not a sidechain. It is not a token. It is Bitcoin used for exactly what Satoshi designed it for: immutable timestamped proof of existence.

**The IBM lineage:** tLog (IBM 4690, 1986–2017) → gLog (elJeffe, 2026–∞)

## 4.2 Layer 2: The Notarization Service (The Operation)

Any network, any webhook, any event — elJeffe:

1. Receives the raw payload at the API gateway
2. Seals it instantly in the PostgreSQL evidence store (milliseconds)
3. Batches recent hashes into a Merkle tree
4. Inscribes the Merkle root into GrowDirect's Ordinal pool
5. Maps every event hash to its position in the tree
6. Returns two responses: **Instant** (hash sealed, chain position assigned) and **Confirmed (~10 min)** (inscription ID, Bitcoin block number, block explorer URL)

GrowDirect's Ordinal is the canonical notarization record. We minted it. We hold the keys. We were there at the Bitcoin block. That cannot be replicated retroactively by any competitor.

## 5.2 The Triple Subscriber Pipeline

*Status: ✅ Written. Source: Condor PRDs TSP-01 through TSP-09. War Chest source: `10-the-architecture.md` (GAP — pull from Condor PRDs).*

Three subscribers. One queue. Competing consumers.

- **Sub 1 (Hash & Seal):** Raw payload → hash → INSERT to `raw_events` → immutability triggers → hash chain
- **Sub 2 (Parse & Route):** Structured parse → Chirp rule evaluation → alert write → Today's View
- **Sub 3 (Merkle & Ordinal):** Batch accumulation → Merkle tree → Ordinal inscription → anchor receipt

Each subscriber is stateless, horizontally scalable, Kubernetes-ready. The queue is the contract. Subscribers compete for messages. No single point of failure.
