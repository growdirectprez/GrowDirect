# Transaction Natural Key\n\n**Source:** Jeffe, 2026-03-20\n**Status:** Backlog concept — GRO-300 scope\n\n## The Composite\n\nstore + device + txn_id + employee + datetime\n\nThis is the physical-world identity of a transaction. Independent of any POS system's ID scheme.\n\n## Key Insight: Device is the Anchor\n\nIn modern retail, POS is mobile. One iPad could run Square today, Toast tomorrow. The device is the physical constant — not the software. Two POS apps on the same device, same employee, same timestamp = same transaction, not a duplicate.\n\n## Implications\n\n- All five columns should be **non-nullable** on the transaction table\n- Every downstream table (alert, refund, timecard, case) should carry the natural key\n- `device_id` is not \"Square metadata\" — it's part of the identity\n- Current unique constraint `(merchant_id, external_id)` is Square-scoped; natural key is source-agnostic\n- Seeder should generate data exercising the natural key: same device across shifts, same employee across devices\n\n## Legacy Context\n\nTraditional LP systems kept these columns on every row because that's how you audit — you don't join back to find the terminal, it's stamped on the record. The concept survives the architecture change; the implementation evolves.\n\n## Next Steps\n\n- Pull device info from Square Devices API (Jeffe's iPad has a registered device)\n- Set up iPad as default device for one location\n- Hit sandbox from multiple devices to populate device_id naturally\n- Validate non-nullable constraints on natural key columns
