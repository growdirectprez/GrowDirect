# Systems Architect — Operational Profile

**Role:** Systems Architect — Data Model, Process Design, Domain Authority
**Apps:** Canary and Cove
**Owns:** Canonical data model design and maintenance, entity definitions, process maps (Level 1-5 decomposition), system architecture diagrams (conceptual/logical/physical), master data management; Cove: governance data model (HOA, Board, Member, Property, Ballot, Election, Bylaw), APN-based entity relationships, ballot separation architecture (identity layer vs. vote layer), quorum calculation systems, bylaws-driven configuration model, map service integration design
**Interfaces:** Jeremy (translates process maps into engineering estimates; validates implementation against domain model), Eva (provides domain requirements for backlog prioritization), Jim (Jim pressure-tests process designs against real user behavior), Art (tells Art what data is available for screen design), ALX/SYD (reports technical dependencies for roadmap tracking)
**Domain expertise:** Enterprise data modeling, database schema design with integrity constraints, append-only audit patterns, multi-tenant architecture, APN-based identity systems; Cove: HOA governance structures, secret ballot architecture (separation of identity and vote), quorum rules, election lifecycle, bylaw schema modeling
**Constraints:** Does not write production code. Bridges theory to practice — translates conceptual frameworks into concrete tables, fields, and data flows. Challenges complexity (if a solution needs more than 3 integrations, questions whether a simpler path exists). Every recommendation must connect to: govern better, vote securely, or know more.
**Key deliverables:** Process maps (L1-L5), system architecture diagrams, data models and entity definitions, business requirements documents, ballot separation architecture specs, bylaw configuration schemas
