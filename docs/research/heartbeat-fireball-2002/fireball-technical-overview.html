Governing Thesis

Heartbeat / Fireball proved, in production, that a near-real-time POS trickle feed plus a per-store-per-SKU statistical velocity model plus a push notification to an operator at the physical point of action is a viable and sufficient shape for demand-signal-driven retail exception detection. The system worked. The deployment model didn't. Canary inherits the design DNA and inverts every commercial failure — self-service onboarding, single-vendor stack, system-tracked alert lifecycle, operator-facing detection thresholds.

Context & NFR Profile

What was deployed, where, at what scale, under whose sponsorship

The system ran at two US grocery deployments. The first was a Tier-1 super-format chain — stores exceeding 250,000 sq ft, approximately 120,000 SKU assortment, 24×7 operations, upper-Midwest geography, piloted at single-department scope (~1,000 monitored SKUs). The second was a southeastern multi-state supermarket chain with approximately 1,100 stores and ~24,000 active SKUs, piloted at full-store scope.

Sponsorship structure — manufacturer, not retailer

The system was sponsored by a global FMCG manufacturer, not the retailer. This matters: the demand-signal thesis was a manufacturer's thesis (supply chain synchronization), and the ROI calculation was a manufacturer's ROI calculation (reduced OOS = fewer lost manufacturer sales). The retailer was the deployment host, not the business-case owner. The commercial misalignment this created was the dominant risk in the Phase-I retrospective.

02

The Problem — Both Layers

The surface problem and the architectural thesis beneath it

The problem was deliberately two-layer. The surface problem was operational: detect out-of-stock conditions from live POS data and notify a store stocker within 15 minutes, before the lost-sale clock compounds. The thesis-level problem was structural: "the supply chain must have a real-time consumer-demand-driven signal that initiates the supply chain response."

OOS was chosen as the wedge problem because it is the most viscerally measurable instance of supply-chain desynchronization from consumer demand. A stockout is a lost sale that every party in the chain — manufacturer, retailer, consumer — feels and can agree to measure. Every design decision in the system follows from prioritizing time-to-actionable-signal over batch sophistication.

Automated reorder or replenishment triggering. Customer-side analytics. E-commerce surface. Self-service onboarding — every retailer deployment required a paid integrator engagement. Vertical generalization beyond grocery.

The "acting on the alert" step was left entirely to the human operator. The system detected and routed. It did not track whether the operator responded. That gap — no system-tracked acknowledgement — is one of the largest single deltas Canary closes.

Architecture & Pipeline

End-to-end data flow, five-cluster hosted service anatomy, two collection patterns evaluated

Five-Cluster Hosted Service Anatomy

Web Cluster

All HTTP/HTTPS connectivity. Interface to EAI bus via receive functions. Customer VPN + FTP. Subscription management UI.

Integration Bus Cluster

Open Channels pattern — destination and transport derived from message body, not hardcoded per-partner configs. SQL-backed routing tables. One port serving many retailers.

Application Server Cluster

Notification subsystem business objects. Subscription state management. Web interface support.

SQL + Analysis Services

Routing and subscription state. Optional POS data mart against standard retail XML model. Optional BI cubes as web service to enterprise customers.

OOS Algorithm Cluster

Detection algorithm + per-installation velocity models. Own XPDB compressed-transaction store — isolated from bus SQL. Returns OOS messages back to the bus.

Architectural decision — two separate stores, deliberately

The OOS cluster maintained its own high-speed XPDB compressed-transaction store — not the bus's SQL cluster. Algorithm's store: recent transaction stream, optimized for velocity computation. Bus's SQL: routing state, subscription state, optional data mart. Two stores, two purposes, no shared write path. This separation was not incidental; it reflects the correct intuition that the detection layer and the routing layer have incompatible access patterns.

Two Collection Patterns Evaluated

PatternMechanicsVerdict
In-store autonomous device Per-store Heartbeat box connected directly to the POS controller. OOS analysis local. HTTP-based reports browseable on LAN. Retained as a product variant. Not the reference architecture.
Centralized hosted service POS data shipped from each store to central hosted service. OOS analysis remote. Results pushed to wireless devices via SMTP. Reference architecture. Won the document footprint. Designed for "internet scale" — multi-tenant across thousands of stores.
Why the centralized pattern won

The in-store autonomous device was a hedge against fragile WAN — rational in 2002 when wide-area connectivity was unreliable. The centralized hosted architecture won because it could support multi-enterprise multi-store deployment against shared infrastructure. Canary chose hosted SaaS outright — the 2002 trade-off is settled in 2026 by commodity cloud and ubiquitous cellular. The edge device option is no longer needed.

04

Detection Algorithm

Poisson velocity model, eight covariates, five event types, feedback-loop retraining

The intellectual centre of the system. Branded as the Consumer Demand Signal Service / Item Velocity Monitor. A statistical-anomaly detector that learned normal item velocity from POS transaction history under varying merchandising conditions, then detected statistical variances from that learned velocity to flag a small set of named event types. Algorithm IP was proprietary to the vendor; transformation specifics were not disclosed.

Most consequential design choice in the entire system

The model receives no inventory feed. OOS is inferred from sales velocity dropping below the model's expectation — not from an inventory-on-hand count crossing zero. This was the design choice that made the system viable at retailers who wouldn't or couldn't provide live inventory data, which was most of them. It also meant the operator receiving an OOS alert had to disambiguate — shelf visit, back-room check — rather than the algorithm.

Five Named Event Types

O — Out of Stock F — Too Fast S — Too Slow N — New Item D — Dropped Item
EventDetection semanticsOperational implication
OOSVelocity dropped to a level statistically inconsistent with learned model under current merchandising conditionsHuman goes to shelf. Algorithm does not disambiguate from "out for restocking."
Too FastItem moving above normal turn rateMisprice, competitor OOS, untracked promotion, or sudden popularity shift
Too SlowBelow normal turn rate, not yet OOS thresholdLeading indicator. System treats OOS as a continuum — Too Slow is the early warning.
New ItemItem code appearing with no prior velocity historyFirst-observation flag for post-distribution tracking
Dropped ItemEstablished velocity model, item has stopped appearingPossible delist or discontinue signal

The Velocity Model — Eight Covariates

A statistical model per (monitored item, monitored store, merchandising condition). Historical item-movement data is transformed into event observations whose arrival times behave as a Poisson process. Eight covariates accounted for in the model:

CovariateWhy it belongs in the model
Current pricePrice elasticity drives velocity. Promotional vs regular price determines expected demand. Without this, every promotion looks like Too Fast.
Time of dayIntra-day patterns differ significantly. Morning vs evening velocity baselines vary by SKU and store format.
Day of weekWeekend vs weekday baseline. Pre-holiday surge. Without this, Sunday patterns look like anomalies every week.
Store identifierPer-store model. Same SKU in different stores can have radically different velocity baselines.
Current store trafficHigh-footfall periods amplify expected velocity. A slow-moving SKU during a quiet period may look OOS when it isn't.
Current promotionsExplicit covariate so a velocity spike during a known promotion does not register as Too Fast.
In-store competitionCompetitive placement context — facing count, adjacent SKU performance.
SeasonalityAnnual and intra-year velocity patterns. A slow summer for a winter SKU should not fire OOS.

Detection Mechanics

For each new transaction: "What is the probability of the newly observed data given the normal velocity model?" Normal velocity already accounts for current conditions. If the probability of the observation — or one more extreme — is sufficiently small, an anomaly event is generated. Classification into event type depends on transaction data and model rules adapted per installation by the vendor.

This is a likelihood-ratio anomaly detector against a learned Poisson model with merchandising-context covariates. Not threshold-based on raw counts. Not a Bayesian network. A parametric statistical model with per-event-type classification overlay tuned per deployment.

Training Feedback Loop

Model is first trained → used to detect events → retrained using events-adjusted historical data. Events filter the training data — observations during a known OOS period are excluded from subsequent retraining so the OOS period does not get re-learned as "normal slow velocity." This conditional data cleaning before each retrain cycle is the quality-gate that prevents the model from chasing its own tail.

Operator tunability boundary — subscriptions, not detection

Operators had subscription knobs, not detection knobs. They could tune what they received (filter by event type, sort order, frequency, time window) but could not adjust the velocity model thresholds directly. All threshold tuning was the algorithm vendor's domain, done per installation. This created an adoption-rate drag — each new retailer required a tuning engagement before detection was production-quality. Canary inverts this: per-merchant detection threshold tuning is exposed directly to the operator via merchant_rule_configs.

Notification Subsystem

Trigger model · subscription model · pager UX · XML schema evolution · failure modes

The operational centre of the system — where detection reached a human who could act. The notification subsystem is the single most directly Canary-parallel artifact in the archive. Every structural dimension maps forward: trigger model, subscription model, delivery channels, report format, event schema, failure modes.

Trigger Model — Three Categories

TriggerWhat fires itSuppressible?
OOS Report Package of OOS, Too Fast, and Too Slow events generated each reporting period. Primary value delivery. Yes — per user
Threshold Alarm Separate alert when cumulative OOS-loss-value crosses a configured dollar threshold (e.g., "$996.36 in OOS losses since last check"). Sent independently so it doesn't get buried in a long event list. Yes — per user (some pilot deployments suppressed this explicitly)
Data Flow Interrupted Fires whenever the trickle POS feed pauses. Signals that downstream OOS reports may be unreliable. The trust-the-pipeline alarm — an operator cannot distinguish "no alerts because nothing's wrong" from "no alerts because we lost visibility" without it. No. Mandatory for all users.

XML Event Schema — Evolution Pattern

The notification subsystem received inputs as XML messages from the OOS cluster. Two schema versions exist in the archive: August schema (6 Aug) and January schema (15 Jan) — a ~5-month delta reflecting production-experience learning. The XML envelope carried routing data inside the message body, not just in headers — the design choice that enabled the EAI bus's Open Channels pattern. One messaging port could serve many retailers because the destination was derived from the message, not from the port configuration.

The Aug → Jan schema delta is the kind of artifact that signals the production deployment surfaced things the design hadn't predicted. Healthy pattern. Canary's CRDM version evolution follows the same arc.

The open loop — what the system did not do

No system-tracked acknowledgement. No alert lifecycle. The operator was expected to open the report, browse events, act at the shelf, and delete the email. Whether they did was out-of-band. The system could not measure its own effectiveness. The Phase-I retrospective noted the notification subsystem worked — the missing piece was the closed-loop signal from operator action back to the system. This is one of the largest deltas Canary closes, with a full alert lifecycle: new → investigating / escalated / resolved / dismissed / case_opened / archived.

Phase-I Retrospective Findings

April 2001 pilot assessment — what worked, what didn't, and why the go-to-market failed while the technology succeeded

The April 2001 Phase-I Pilot Assessment by the integration vendor's consulting arm was the most honest document in the archive. The central finding: the technical system worked. The go-to-market did not. Business-model risks dominated the retrospective's risk register — not delivery-quality risks.

✓ Design decisions that aged well
✓Trickle feed as foundation. Continuous near-real-time POS event arrival as the non-negotiable prerequisite. Still axiomatic in 2026 — Canary's TSP webhook design starts from the same axiom without re-litigating it.
✓Operator as final recipient. Route to a human at the physical point of action. No automated remediation in the data path. Canary preserves this — Chirp alerts, Fox investigates, humans close the loop.
✓Per-(item, store) baseline. Velocity learned at per-store-per-SKU granularity — not aggregated across the chain. Granularity is detection quality. Still the right choice.
✓Subscription / filter / sort tunable per user. The system understood that one alert shape per organization fails. Different roles — stockers vs managers — need different filters and sort orders.
✓Non-suppressible Data Flow Interrupted alarm. "No alerts" is ambiguous without a pipeline-health signal. An operator can't distinguish "fine" from "blind."
✓Open-routing pattern. Destination derived from message content. Made multi-tenant routing work. Still load-bearing in every SaaS event pipeline in 2026.
✗ Design decisions that failed (or were right-for-2002)
✗Deployment cost. Every retailer required a paid integrator engagement. Retrospective explicitly: "no turnkey solution that would allow rapid adoption." Right-for-2002; a business-ending constraint for SMB SaaS.
✗Three-party commercial dependency. FMCG sponsor + integration vendor + algorithm vendor had to align before any retailer could deploy. Top-line risk in the retrospective. Canary owns the entire stack.
✗No system-tracked operator acknowledgement. "Did the operator act?" was out-of-band. System could not measure its own effectiveness. Canary brings it inside with a full alert lifecycle.
✗Detection thresholds hidden from operators. Subscription knobs only — no detection knobs. Algorithm tuning was the vendor's domain, per installation. Adoption-rate drag. Canary exposes thresholds directly via merchant rule configs.
✗In-memory event cache only. No durable event store, no replay. Historical record was the optional data-mart copy — separate system, not authoritative. Canary's append-only evidence_records table is the durable, replayable, forensic-grade ground truth.
✗Algorithm scalability open question. Per-(store, SKU) Poisson model with 15-min retrain and 8 covariates was computationally non-trivial at full-store super-format scale (~120k SKUs). Performance under full assortment coverage was not proven in the pilot.
The retrospective's most important line

The notification subsystem was on track and working. The independent algorithm audit at the southeastern-chain pilot was on track. The delivery risk was low. The risks that dominated the register were: ROI schedule communication, commitments to next-round pilots, investment recoupment, and escalating requirements without clear ROI attribution. The technology proved out. The commercial model — three-party, high-deployment-cost, manufacturer-sponsored — did not.

The architectural shape — unchanged in 25 years

Near-real-time detection produces an event → event flows through an integration layer → subscription subsystem determines who and how → message renders for the receiving channel and context → operator acts at the physical point. The 2002 design got this shape right. Canary inherits it without significant alteration. The substrate changed. The design DNA didn't. What Canary adds is the closed loop — system-tracked operator response, investigation lifecycle, cryptographic evidence chain — that 2002 left outside the system boundary by necessity.
