# Audit Proof Verification

**URL:** `/transactions/:id/proof`  
**Primary role:** LP; ADM; external auditor  
**Entry points:** Transaction detail → "View Audit Proof" action; case evidence review

## Layout

| Zone | Content | Notes |
|---|---|---|
| Header | "Audit Proof: Ticket #[id]", back link to transaction detail | |
| Verification status banner | Full-width — VERIFIED (green) or TAMPERED (red) | Most important element |
| Main content | Three panels: Transaction Hash, Merkle Path, Anchor Record | Left to right |
| Action bar | Verify Now (re-run), Export Certificate (PDF), Copy Hash | |

## Key Elements

### Verification Status Banner
Two states:
- **VERIFIED (green):** "This transaction record has not been modified since ingestion. All proofs are valid."
- **TAMPERED (red):** "This transaction record does not match its original hash. Data may have been modified after ingestion. This is an LP event — create a case immediately."

### Transaction Hash Panel
- Record hash (SHA-256) — full 64-character string + copy button
- Hash algorithm: SHA-256
- Computed at: timestamp of ingestion (T.2.3 ingest moment)
- Current hash: recomputed on every page load (comparison basis)
- Match status: ✓ Hashes match / ✗ Hash mismatch

### Merkle Path Panel
Proof of inclusion in the audit Merkle tree:
- Transaction leaf hash
- Sibling hashes (path from leaf to root)
- Root hash for this audit batch
- Batch timestamp
- Verification result: ✓ Inclusion proven

This panel is for auditors who want to verify the proof independently, not for daily LP use. Collapsed by default with an "Advanced — Show Merkle Path" expand.

### Anchor Record Panel
If S4 (blockchain) anchoring is active:
- Batch root hash
- Blockchain transaction ID (external link to block explorer)
- Anchor timestamp
- Chain: [configured chain name]
- Status: ✓ Anchored / ⏳ Pending anchor (< 24h old)

If not yet anchored: "Pending blockchain anchor — new records are anchored every 24 hours. Merkle proof is valid regardless of anchor status."

### Exportable Proof Certificate
PDF export. Contains: transaction summary (ticket #, store, cashier, date, total), hash, Merkle proof summary, anchor record (if available), verification status, export timestamp, and a plain-language attestation: "This certificate was generated by Canary and confirms that the transaction record identified above has not been modified since ingestion."

Used for: HR proceedings, police reports, insurance claims, SOC 2 audit evidence.

## Interaction Flows

1. **Pre-HR-meeting verification:** LP preparing a case for HR → navigates to each evidence transaction → clicks View Audit Proof → exports PDF certificate for each → includes certificates in HR package
2. **SOC 2 audit demonstration:** ADM demonstrating Canary's integrity model to auditor → opens a transaction → shows audit proof screen → exports certificate → auditor independently verifies hash → audit satisfied
3. **Tamper detection:** LP opens proof screen → TAMPERED banner → immediately creates a case with the tamper event as primary evidence → escalates to management and legal

## UX Callout

This screen will be opened rarely — and that rarity is a feature, not a limitation. On the days it's needed (HR hearing, police report, insurance claim, audit), it is irreplaceable. Counterpoint operators have nothing equivalent to show: their transaction history is a read-only database view with no integrity guarantee whatsoever. A CP LP team presenting evidence to HR is presenting printouts from a form that anyone with database access could have altered. Canary's audit proof certificate is a cryptographic attestation. The design principle for this screen is: every element should be legible to a non-engineer who needs to explain it in a legal or HR context.
